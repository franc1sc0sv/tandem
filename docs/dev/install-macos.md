# Installing Tandem on macOS

`Tandem.app` carries the agent inside: `Contents/MacOS/tandemd`. The app installs a LaunchAgent
that starts `tandemd` at login, and on first launch it guides the permissions macOS
asks for to capture and inject keyboard and mouse.

## Install

1. Open `Tandem_<version>_<arch>.dmg` (from the CI artifact `tandem-macos-dmg`, or from the one
   generated by `scripts/macos/bundle.sh`) and drag **Tandem** to **Applications**.
2. The first time, since the signature is self-signed, not Developer ID (see [Signing](#signing)),
   Gatekeeper does not open it with a double click: right click → **Open** → **Open**. On macOS 15 or later, if the option does not
   appear: **System Settings → Privacy & Security → Open Anyway**. From a
   terminal, removing the quarantine also works:
   ```sh
   xattr -dr com.apple.quarantine /Applications/Tandem.app
   ```
3. Open it **from Applications**. If it is opened from the disk image or macOS runs it
   from a temporary copy (*App Translocation*, which happens to quarantined apps outside
   Applications), the app does not install the agent and says so in the guide: the LaunchAgent would point
   to a path that disappears.

No configuration needs to be written. The first time it starts, `tandemd` creates
`~/Library/Application Support/Tandem/tandem.toml` with what it sees (see
[Automatic configuration](#automatic-configuration)).

## Automatic configuration

If there is no `tandem.toml`, `tandemd` generates it at startup (`tandemd::autoconfig`, T-082):

- `machine = "mac"`;
- the empty desk: no `[[screens]]`, the input engine uses the screens macOS reports
  to move the cursor and the Mac goes to the left of the PC (DESIGN §7);
- network, input and power with their default values (port 52000, no fixed links, no
  Wake-on-LAN or hub: nothing made up).

Tandem does not control monitors (DESIGN §8): it does not change inputs or turn screens off. If the
default arrangement does not match your desktop, declare the screens by hand with
`[[screens]]` (id, x, y, width, height in that machine's cursor coordinates, and scale)
and `[arrangement]` (`mac_side`); the change reaches the other machine with the desk. The file can
be edited (format in `crates/tandemd/src/config.rs` and `docs/examples/tandem.mac.toml`);
while it exists, the agent does not generate it again. A v0.1 `[[monitors]]` section is
ignored with a warning in the log. To validate one edited by hand:

```sh
/Applications/Tandem.app/Contents/MacOS/tandemd --check-config ~/Library/Application\ Support/Tandem/tandem.toml
```

If the configured UDP port cannot be opened, the agent tries others (52000, 52100, 53100…,
always outside 47000–48999) and announces the real one over mDNS. If none opens, the log says which ones it
tried and how to choose another in `[network] port`.

## The login agent

Every time it starts, the app brings `~/Library/LaunchAgents/com.franc1sc0sv.tandem.tandemd.plist`
up to date (`tandem_ui::launch_agent`):

- it points to the `tandemd` of the app that is running and carries its version
  (`TANDEM_APP_VERSION`): updating the app changes the plist, and the app takes the old agent out
  of launchd (`launchctl bootout`) and loads the new one (`launchctl bootstrap gui/<uid>`);
- if the plist is already correct, loaded and `tandemd` is running, it touches nothing (opening the
  app does not restart `tandemd`); if it is loaded but has no process, it starts it
  (`launchctl kickstart`, T-331); if it is there but not loaded, it loads it again;
- while the app is open, if the window finds nobody on the IPC three times in a row and launchd has
  the agent loaded without a process, the app starts it, at most once every 30 s (T-331);
- `AssociatedBundleIdentifiers = [com.franc1sc0sv.tandem]`: macOS takes the app as the code
  responsible for `tandemd`, which is what makes it show the Local Network alert for a
  LaunchAgent that is not installed with `SMAppService` (T-344, see [Local Network](#local-network-t-344));
- `RunAtLoad`, `KeepAlive = true` (relaunched however it ends, also with exit code 0; T-332),
  `ThrottleInterval` of 30 s, only in the graphical session (`LimitLoadToSessionType = Aqua`). To
  stop it for good, take it out of launchd (`launchctl bootout`, as in "Uninstall"): killing the
  process only restarts it;
- `tandemd`'s output before opening its log goes to `~/Library/Logs/Tandem/tandemd.log`; its own
  log, to `~/Library/Application Support/Tandem/logs/`.

How it ended up can be seen on the permissions guide's first screen (the **Permissions** button of the
window). By hand:

```sh
launchctl print gui/$(id -u)/com.franc1sc0sv.tandem.tandemd   # state, PID, last exit code
launchctl kickstart -k gui/$(id -u)/com.franc1sc0sv.tandem.tandemd   # restart it
```

## Permissions

`tandemd` is the one that captures and injects, so the permissions are its own. The first-launch guide
(`tandem_ui::setup`) shows one screen per permission with a button that opens the corresponding panel
of **System Settings → Privacy & Security**; it is reopened with the
**Permissions** button. Pressing **Finish** marks it in
`~/Library/Application Support/Tandem/setup.done` and it does not come up on its own again.

| Permission | What for | Panel |
|---|---|---|
| Accessibility | Injecting keyboard and mouse coming from the PC; "Bring windows" | `Privacy_Accessibility` |
| Input Monitoring | Capturing the Mac's keyboard and mouse to send them to the PC | `Privacy_ListenEvent` |
| Local Network | Discovering the PC over mDNS (`_tandem._udp`) and talking to it over QUIC; probed by the agent ([below](#local-network-t-344)) | `Privacy_LocalNetwork` |

### Flow to grant Accessibility and Input Monitoring (T-090)

macOS grants these permissions to a specific binary, and the one that counts is the one that runs:
`tandemd`, launched by the LaunchAgent. That is why the app does not depend on adding it by hand:

1. At startup, `tandemd` asks once for the missing permissions (macOS shows its dialog, and
   this registers the real binary). After that it only asks with the **Ask for permissions** button,
   never in a loop.
2. Step 1 of the setup ("This machine") and the **Permissions** guide show the state the
   agent reports, and "Grant the permission to this binary: `<path>` (pid N)". That path and that
   pid are those of the running process, not a guess.
3. Grant the permission in **System Settings → Privacy & Security → Accessibility** and **Input
   Monitoring**. If `tandemd` does not appear, press **Ask for permissions** first; as a last resort
   **+** and the path shown (⌘⇧G to type it).
4. Press **Restart agent** (`launchctl kickstart -k`, no terminal): macOS evaluates part of
   the permissions once per process, so what was granted applies in the new process (the pid
   changes). The "permissions missing" notice goes away on its own.
5. If it was enabled and is still missing, the entry belongs to another version or path: remove it with
   **−**, press **Ask for permissions** and restart the agent.

Two warnings: **Restart agent** with the permission still not granted asks for it again in the
new process, and macOS may show its dialog again. And protocol v14 requires updating
Mac and PC at the same time: a v13 agent rejects the link with `IncompatibleVersion`.

Pending hardware verification of this flow: `docs/tasks/T-090.md`.

In Accessibility and Input Monitoring, if `tandemd` does not appear in the list, press **+**
and choose `/Applications/Tandem.app/Contents/MacOS/tandemd` (⌘⇧G to type the path).

### Local Network (T-344)

A LaunchAgent is not exempt from local network privacy (daemons, root and anything started from
Terminal are), and macOS has no API that reads the permission. Research and sources:
`docs/research/macos-local-network.md`. How Tandem handles it:

1. The LaunchAgent names the app in `AssociatedBundleIdentifiers`, so the alert and the System
   Settings entry should be Tandem's. The alert's text comes from
   `NSLocalNetworkUsageDescription` (`apps/tandem-ui/src-tauri/Info.plist`). macOS may still show
   the entry as `tandemd` (an Apple bug, FB16563823): turn on whichever appears.
2. At start-up `tandemd` sends one empty UDP datagram to `224.0.0.251:9`. That brings up the
   alert if macOS never asked, and it is repeated every 5 s while the permission is missing (60 s
   once granted), so a permission granted in System Settings is seen without restarting the agent.
3. The agent reports **granted** (the send went through), **denied** (macOS kept answering
   `EHOSTUNREACH` for 20 s, or right after it had worked) or **unknown** (not tried yet, no
   network, or the alert may still be on screen). macOS gives the same error while its alert is
   up and after "Don't Allow", so time is what tells them apart.
4. Step 3 of the setup shows that state, with **Ask again** (the agent tries at once) and **Open
   settings**. When it is denied, the pairing step and the Network screen say "Local Network
   permission missing on this Mac" with the path to the setting, instead of waiting for the other
   machine forever.

macOS asks only once. After "Don't Allow", **Ask again** cannot bring the alert back: turn on
Tandem (or `tandemd`) in **System Settings → Privacy & Security → Local Network**. On macOS 27.2 or
later the list has **−**, which resets the entry so the alert can come back. A configuration
profile (MDM) cannot grant this permission. A machine running `tandemd` from Terminal uses
Terminal's permission instead, which is why that works when the LaunchAgent does not.

Checking it by hand:

```sh
launchctl print gui/$(id -u)/com.franc1sc0sv.tandem.tandemd | grep -A2 AssociatedBundleIdentifiers
grep "local network" ~/Library/Application\ Support/Tandem/logs/*   # what the probe found
```

macOS keeps each permission for the code that satisfies the designated requirement stored when it
was granted. Release builds are signed with a stable self-signed identity (T-348), so **updates keep
Accessibility, Input Monitoring and Local Network**: every version has the same requirement
(identifier + certificate). Two exceptions: the first update from an ad-hoc build (released before
T-348) asks once more, and a local build from `scripts/macos/bundle.sh` is ad hoc, which macOS ties
to that exact build (remove the old entry from the list and add the new one). Details:
[release.md](release.md#macos-signing-identity).

Useful commands when testing:

```sh
tccutil reset Accessibility com.franc1sc0sv.tandem   # forget the app's permission
rm ~/Library/Application\ Support/Tandem/setup.done   # see the guide again on opening
```

## Building the .dmg

On a Mac with Rust, Node 22 and pnpm:

```sh
pnpm --dir apps/tandem-ui install
scripts/macos/bundle.sh
```

The script compiles `tandemd` in release for the machine's target (or `TANDEM_TARGET`),
leaves it as a sidecar at `apps/tandem-ui/src-tauri/binaries/tandemd-<target>` (not versioned),
runs `tauri build --bundles app,dmg` with `src-tauri/tauri.sidecar.json` (which adds the
sidecar; outside the script the app compiles without it) and checks that the app carries `tandemd`, that the
`Info.plist` has the local network description, the signature (`codesign --verify --deep --strict`)
and the image (`hdiutil verify`). Result in
`target/<target>/release/bundle/dmg/Tandem_<version>_<arch>.dmg`.

The `dmg (macos-latest)` CI job does the same on every PR, signed with a disposable self-signed
identity, checks with `scripts/macos/dr-check.sh` that a second version keeps the designated
requirement, and uploads the `.dmg` as the artifact `tandem-macos-dmg` (Apple Silicon).

## Signing

**User's decision:** no Apple Developer account. Release builds are signed with the **stable
self-signed identity** of the repo secrets (T-348, [release.md](release.md#macos-signing-identity)):
macOS keeps the privacy permissions across updates and Gatekeeper asks to confirm the first
opening. Local builds stay **ad hoc** (`"signingIdentity": "-"` in
`apps/tandem-ui/src-tauri/tauri.macos.conf.json`); to sign one like a release, import an identity
with `scripts/macos/keychain.sh import` and pass its SHA-1 as `APPLE_SIGNING_IDENTITY`. Tauri's
bundler also signs the sidecar.

To sign with **Developer ID** and **notarize**, it is enough to define the variables read by
Tauri's bundler before `scripts/macos/bundle.sh` (in CI, as repo secrets):

| Variable | What it is |
|---|---|
| `APPLE_SIGNING_IDENTITY` | Signing identity, e.g. `Developer ID Application: Name (TEAMID)`. Replaces the ad-hoc one |
| `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD` | The `.p12` certificate in base64 and its password, if it is not already in the keychain (CI) |
| `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID` | Notarization with Apple ID and app password |
| `APPLE_API_ISSUER`, `APPLE_API_KEY`, `APPLE_API_KEY_PATH` | Or notarization with an App Store Connect key |

With a real identity and notarization credentials, `tauri build` signs with *hardened runtime*,
notarizes and staples the ticket; Gatekeeper opens the app without asking and privacy
permissions survive updates. Without notarization credentials, it signs but does not
notarize.

## Uninstall

```sh
launchctl bootout gui/$(id -u)/com.franc1sc0sv.tandem.tandemd
rm ~/Library/LaunchAgents/com.franc1sc0sv.tandem.tandemd.plist
rm -rf /Applications/Tandem.app
# Optional: configuration, state, identity and logs.
rm -rf ~/Library/Application\ Support/Tandem ~/Library/Logs/Tandem
```

And remove `tandemd` and Tandem from the Accessibility, Input Monitoring and Local
Network lists.
