# Decisions

Record of product and architecture decisions. What is here overrides any task; `DESIGN.md` develops it.
Each entry carries a date and who decided: **user** (explicit answer) or **agent** (decided without the user, to be reviewed).

Agents that work alone (for example overnight) **do not ask**: they look for the answer in this file, then in `DESIGN.md`, then in the mockups (`mockups/v03/`). If nothing settles it, they decide the simplest thing that respects all of the above and add an entry at the end of the "Decided by agents" section, with the reason.

## v0.3 (grilling of 2026-11-16)

### Product

| # | Decision | Who |
|---|---|---|
| D1 | **Exactly two machines, peer to peer (P2P).** There is no third machine nor "add machine"; the other one can be **changed** (pair again). | user |
| D2 | **Nothing tied to Mac or PC.** Each side can be macOS or Windows; the code does not assume which system is on each side. What a machine can do comes from its announced **capabilities**. | user |
| D3 | **Modules compiled per system + capabilities.** Each module exists only where it compiles; at runtime it announces whether it is active, off or unavailable, with its reason. | user |
| D4 | **All configuration from the UI**, synced between both. `tandem.toml` remains as storage, not as an interface. | user |
| D5 | **Configuration conflicts: the last one to save wins.** The other machine shows a notice with "Undo" (short history). There is only one user: no question is asked. | agent (the user said it won't happen) |
| D6 | **Scenes instead of modes.** A scene saves what each monitor shows and the arrangement; it is applied as a transaction. | user |
| D7 | **Keyboard and mouse with no owner:** they work from either machine and Tandem follows the one in use. There is no "Keyboard here" in the UI. | user |
| D8 | **Tunnels:** Claude opens tunnels between the two machines through **MCP + CLI** and does whatever inside: several processes, files, ports, git workspaces that come back as a branch. They survive the link dropping. They run with the highest privileges the agent has. Detected environments (shells, WSL, Docker, toolchains). | user |
| D9 | **The tunnels UI is read-only:** Claude manages them; the app shows projects, tunnels, running processes and their output. | user |
| D10 | **Nothing specific to one computer** (nothing about "the RTX 5080"): everything comes from the machine's scan. | user |
| D11 | **Monitors: a single standard.** A monitor is controlled if it speaks the own-firmware protocol (the 34"'s); otherwise it appears as "not supported" until it gets its patch. No factory profiles and no guessing. | user |
| D12 | **Monitor control is Rust, in a crate of the `monitor-firmware` repo**, used by both agents (same code on macOS and Windows). | user |
| D13 | **One owner per monitor, chosen automatically:** the machine with a working DDC channel reads and controls it; the other asks over the control plane. If the owner leaves, another is chosen. | user |
| D14 | **New module: drag files between machines** when crossing the edge. No audio or notifications for now. | user |
| D15 | **⌘K / Ctrl+K palette: Tandem commands only** (no natural language). | user |
| D16 | **Sidebar navigation** (Desk, Tunnels, Monitors, Arrangement, Network, one page per machine, Settings). | user |
| D17 | **Color per machine:** assigned automatically when pairing, editable. | user |
| D18 | **Arrangement:** the other machine is placed on **any of the 4 sides** with alignment (start, center, end); no manual X/Y. Mockup `V3-Arrangement`. | user |
| D19 | **Unsigned release + automatic update** from GitHub Releases. No new power extras. | user |
| D20 | **Order:** foundations → input → tunnels → monitors → live UI → USB-C → release. | user |

### Architecture (decided by the agent when planning, 2026-11-16)

| # | Decision | Reason |
|---|---|---|
| A1 | **`Machine::{A, B}` instead of `Machine::{Mac, Pc}`.** The two sides are ordered by Ed25519 public key (the lower one is `A`), so both machines agree without coordinating. Each side's system, name and color come from its announcement. | D1 + D2 with the smallest change: the code is already two-sided (`machine.other()`); only the assumption about the system is removed. |
| A2 | **Data can go over Wi-Fi.** "Wi-Fi never carries data" is removed. Input always has priority: data (tunnels, files) goes in low-priority streams and with a bandwidth cap on Wi-Fi so as not to add latency to keyboard and mouse. | D8 asks for robust tunnels over any network, and today there is no working USB-C cable (see A6). |
| A3 | **New UI in Svelte 5 + Vite** (inside Tauri 2). The pure logic that already exists in TypeScript is kept and tested with vitest. | The redesign has ~20 screens with state and animations; hand-written DOM does not scale. Svelte brings transitions and is light. |
| A4 | **Design tokens from the v0.3 mockups** (`mockups/v03/`): colors, button system, line icons, animations with `prefers-reduced-motion`. The mockups are the visual reference; each screen is compared with its mockup by screenshots. | Single visual source of truth. |
| A5 | **The monitor crate is called `monitor-ddc`** and lives in `monitor-firmware/crates/monitor-ddc`. Tandem uses it as a git dependency pinned by commit. The `monitor-firmware` repo uses the `develop` integration branch with the same rules as Tandem (never touching `main`). | D12. |
| A6 | **USB-C gives no link today (spike S5, 2026-11-16).** With the 10 Gbps cable both ends negotiate over PD and the PC advertises USB4, but the USB4 link never trains; with a USB 2.0 one it is impossible. The user does not want to update the BIOS (F3, ASM4242 firmware from 2024-05). A 40 Gbps Thunderbolt 4 / USB4 cable will be tried. Meanwhile the daily link is Wi-Fi (and Ethernet if added). T-094 is written and tested with simulators; the physical part stays in its hardware list. | Facts measured with `ioreg` on the Mac and PnP/registry on Windows. |
| A7 | **Tunnel privileges:** the process runs with the agent's privileges. On Windows the agent starts elevated (scheduled task "with highest privileges", no SYSTEM service while T-027 waits for the user); on macOS it runs as the user. | D8 ("always as admin") without depending on T-027. |
| A8 | **Overnight hardware tests allowed**, with mandatory automatic revert on anything that changes a monitor input (an independent watchdog restores it). The Mac is used through `ssh mac-runner` (Wi-Fi). | The user authorized it. |
| A9 | **Mockups with three machines** (`F-AddHost`, the example MacBook Air) are out because of D1: instead, "Change the other machine" (pair again). | D1. |

- 2026-11-17 · T-105 · The tools of a Unix shell and of each WSL distro are searched by running a POSIX script inside that shell as interactive and login (`-lic`, and `-lc` if that fails), not with the agent's `PATH` · launchd and the Windows scheduled task do not carry the user's `PATH` (Homebrew, `~/.cargo/bin`, fnm/nvm are loaded from the rc); it is the same a tunnel process will see.

- 2026-11-17 · T-105 · The other machine's resources are requested with `ControlMsg::WatchResources` as a lease: whoever watches renews it every 3 s and the other stops sending after 10 s without renewal (or at once with `on: false`) · this way it does not depend on learning that the link dropped nor on the order in which the two machines see the reconnection.
- 2026-11-17 · T-105 · The UI's subscription to resources belongs to the IPC connection (`UiCommand::WatchResources`) and is dropped when it closes; there is no standalone `GetResources` · sampling at 1 Hz only with subscribers requires knowing when nobody is watching; the MCP `resources` tool (T-108) can request, read one sample from each machine and close.
- 2026-11-17 · T-105 · On Windows the `Win32_VideoController` GPUs that `nvidia-smi` does not describe (the integrated AMD/Intel) are also listed, with their memory only if `AdapterRAM` is not truncated (32 bits, ~4 GiB) · D10: everything the computer has, without assuming one; `nvidia-smi` gives the real VRAM of NVIDIA ones.
- 2026-11-17 · T-101 · The data cap over Wi-Fi is the desk's `[data]` (`wifi_cap_percent`, 50 by default; optional fixed `wifi_cap_mbps`); with no measurement 20 MB/s is assumed (cap of 10 MB/s) until T-102 measures · the latency pause is fed only with the real input latency (T-093), not with the pings' RTT: with idle Wi-Fi the RTT rises and the pause would never end.
- 2026-11-17 · T-101 · One `Qos` per path (the agent's `LinkQos`), shared by the connection each agent opens and those it accepts; besides the configured cap, the part in use is adjusted by latency: with the input's p99 above 75 % of the target it goes down (×0.7, or ×0.5 once past the target, at most once per window), between 50 and 75 % it stays, and with headroom it goes up 25 % per second; a pause leaves it at half and a new measurement returns it to full · #73 review: with a Wi-Fi that worsens and stays bad, pausing and resuming with the same cap went into a cycle every ~4 s, and two connections per path used double the cap.
- 2026-11-17 · T-122 · The updater runs in the UI (Rust, `tauri-plugin-updater`) and `tandemd` only counts versions and passes the "install X" request to the other's UI (`ControlMsg::Update`, `UiCommand::UpdatePeer`/`GetUpdate`, `AgentToUi::Update`) · each system's package carries both binaries and the plugin already knows how to download, validate and install; duplicating it in the agent adds nothing.
- 2026-11-17 · T-122 · "Update all" does not move the keyboard: "without cutting it" means one at a time and waiting for the other to come back (up to 10 min) before restarting this one; if it does not come back, this one is not touched · `SetKeyboard` declares where the physical keyboard is, not where the cursor goes; moving that declaration would break the configuration.
- 2026-11-17 · T-122 · The other coming back speaking another protocol version counts as "came back updated" (`UpdateStatus::peer_protocol`) · almost every release bumps `PROTOCOL_VERSION`, and then the old machine cannot hear the new version.
- 2026-11-17 · T-122 · "Update automatically" (on by default, in `update.toml` separate from `ui.toml`) is only led by `A`; with no peer, each one alone · a rule both know without talking; `shortcuts::save` rewrites the whole `ui.toml`.
- 2026-11-17 · T-122 · Prereleases (`-rc.N`) stay as drafts and do not reach the updater (`releases/latest` ignores drafts and prereleases); final versions are published automatically when the workflow ends · the task asks to publish (draft → published) and to test the rcs as drafts.
- 2026-11-17 · T-093 · D7 arbitration by messages between agents (`ControlMsg::Focus`): the one that is not in charge and receives physical input asks for the keyboard (at most every 50 ms), the one in charge yields it if it has gone 300 ms without its own physical input; each change bumps an epoch and with different views the greater epoch wins and, if tied, `A`'s. With no link, the one in use is in charge · deciding on one side at a time avoids both believing they are the server; the epoch resolves what was decided without a link on return.
- 2026-11-17 · T-093 · The hub no longer decides who is in charge: it is only informational (`hub_here`, `defined`); what is declared (configuration or setup) says with whom to start and forces a new epoch · D7: physical input rules, and moving the hub to another machine already produces physical input on the other.
- 2026-11-17 · T-093 · Both machines always have capture running (the one not in charge consumes it without crossing) · D7 needs it to know there is physical input; on macOS it asks for Accessibility also on the one not in charge (it already asked for it to inject).
- 2026-11-17 · T-093 · The movement delta travels in the client's native units (before, logical points) · the server already computes it screen by screen; in logical units, a datagram that merged movement across screens of different scales left the client in a different place than the server (test "lossless: client matches server across scales").
- 2026-11-17 · T-093 · Dragging between machines: by default the cursor does not cross with a button pressed (like Deskflow); it is enabled with `[input] drag_between_machines = true` until T-099 moves it to the shared desk · the preference belongs to the desk (T-099), but the engine needs it now.
- 2026-11-17 · T-093 · Immediate send instead of touching `TransportConfig`: each captured batch goes out right away as a datagram (`send_datagram` does not wait), and only what arrived while the previous one was being sent is merged. With input only, quinn 0.11's *pacing* does not slow it down (minimum burst of 10 packets and refill at the window-per-RTT rate); with data on the same connection it is T-101's work · quinn does not allow skipping *pacing* per datagram without disabling congestion control for the whole connection. The `tandem-input` thread isolates capture, the queue and injection, not the output: UDP is still emitted by quinn's connection driver on the main runtime (T-101's work).
- 2026-11-17 · T-102 · The bandwidth test runs without the data cap but respects the pause: if the path's `Qos` pauses data (input went past its target), the test is cut and rejected ("input went past its target") · measuring through the cap would give the cap, and 3 s without a pause over the active path on Wi-Fi fill the access point's queue and stall keyboard and mouse (DESIGN §6)
- 2026-11-17 · T-102 · The duration of a path switch (`took`) is counted from the last response of the path that dropped: it is an upper bound of the cut (with 1 s pings and a 250 ms timeout, ~1.25 s) · it is not known when it really dropped, only when it last responded
