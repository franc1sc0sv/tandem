# T-065 — Hysteresis when returning to the preferred link

## Scope

The manager returns to USB4 as soon as it answers; an intermittent USB4 can end in `Inconsistent` even though Ethernet is healthy (QA round 2 observation).
Add hysteresis: the preferred link must be healthy for a configurable time (e.g. 3 s of good pings) before returning to it; never switch links in the middle of a transaction unless the current one drops.

## Acceptance criteria

- [x] Test: a USB4 that cuts out and comes back every 700 ms causes no link switches while Ethernet is healthy.
- [x] Test: after 3 s stable, it returns to USB4.
- [x] The tandem-sim test `usb4_intermitente_durante_un_cambio` always ends clean.

## Notes

- `tandem-link::manager`: `HealthConfig::settle` (3 s by default; 0 disables it). The table receives the time and whether a transaction is in progress as arguments, so it stays pure and is tested with properties.
- Rule: if the active link drops, switch instantly (also in the middle of a transaction). Moving up to a better link is only done with no transaction in progress and, if that link has ever dropped while healthy, after `settle` of consecutive good pings. A link that never dropped is taken right away, so startup does not stay 3 s on Wi-Fi because its first ping arrived earlier. With no healthy active link the best stable one is chosen and, if there is none, any healthy one (better a flickering one than none).
- Transactions: `LinkManager::hold()` returns a hold (RAII); when the last one is released it re-evaluates immediately. In `tandemd`, `PeerLink::hold_link()` (`None` by default) and the `Orchestrator` takes it in `try_begin` and releases it in `end`. Only the machine that orchestrates holds it: the one that performs steps for the other answers over the connection the other opened.
- Known limit: with pings every 1 s, a cut that falls entirely between two pings is not seen (QUIC survives short cuts). With a 700 ms flicker there are never four consecutive good pings, so it does not reach 3 s.
- Tests: table (flicker every 700 ms with a single switch to Ethernet, return at exactly 3 s, hold, properties with random time and transactions); manager with paused clock (30 s of flicker in six phases without events and return ≤ 4.1 s; hold); orchestrator (holds during the transaction); `usb4_intermitente_durante_un_cambio` now demands a clean outcome across 14 offsets and that the active link stays on Ethernet while it flickers (it fails without the hysteresis).
