# T-028 — Synchronized clipboard

## Scope

`tandem-clipboard`: per-platform change detector, read/write with arboard (text, HTML, image), echo suppression by hash, lazy transfer over the reliable stream.

## Acceptance criteria

- [x] Tests of echo suppression and of the protocol with simulated clipboards.
- [x] Platform implementations compile on CI.

## Notes

- Pieces: `ClipContent` (text, HTML, RGBA image) with its SHA-256 hash; `ClipSync`, a state machine without I/O and identical on both agents; the `Clipboard` trait (change counter, read, write) with `SystemClipboard` (arboard) and `fake::FakeClipboard`; and `ClipDriver`, which ties them together with a `tandem-link` `ControlStream`.
- **Protocol** (`msg::ClipMsg`): `Offer` announces each copy with hash and size; if it is small (≤ 64 KiB encoded) it goes inside and the other side writes it on arrival. Otherwise the transfer is lazy: it is requested with `Request` when the machine **has the focus** of the keyboard and mouse (that is when the user can paste) and arrives in 256 KiB `Chunk`s; `Unavailable` if the owner has already copied something else. arboard does not allow the system's *delayed rendering* (supplying the data at paste time), so "on paste" is approximated with "on taking focus". Cap of 128 MiB per copy.
- **Echo suppression**: the hash of what the local clipboard holds (seen or written) is remembered; a change with that hash is not announced and an offer with that hash is not written. In addition, after writing, the driver takes the system's change counter as the baseline, so the write itself is not even read (this covers the system converting it, like Windows's HTML with a CF_HTML header).
- **Crossed copies**: each copy's id is a Lamport clock (greater than everything seen from the other side) with the wall clock as a floor, and the hash breaks ties. Each side accepts only an offer greater than the current one, so two simultaneous copies end up the same on both sides, a copy made after seeing the other always wins, and a restarted agent does not end up below. A property (`proptest`) proves it with two agents, queues, focus and link changes that lose what was in flight: they always converge, without echo and with finite messages.
- **Between sessions**: the state survives the link change. On starting, what was copied without a link is announced or the current own copy is re-announced (in case the announcement was lost); what is pending from the other side is requested again.
- **Change detector**: `NSPasteboard.changeCount` on macOS and `GetClipboardSequenceNumber` on Windows, polled every 250 ms (cheap; the content is only read when it changes). On Windows it was preferred over the research's `AddClipboardFormatListener` because that one needs a window and its message loop for the same thing. On Linux (not a target) the counter compares the content.
- **Writing**: arboard replaces the whole clipboard on each write, so text and image cannot be put together: text wins (with its HTML); the image is written if there is no text.
- **Own stream**: the clipboard goes over a bidirectional stream separate from the input one, so that a large image does not delay the keys. `ControlStream::split` was added in `tandem-link` (with a test of both sides sending more than fits in QUIC's windows at once): the driver keeps reading while flow control throttles a transfer, so two sides writing do not block each other.
- Still to be wired in `tandemd` (like T-026's input session): open/accept the clipboard stream over the active link's connection in a fixed order relative to the input one, pass the focus (`with_focus`, `true` when the cursor is on this machine) and the link manager's `stop`. The clipboard calls are blocking and short; with large images it is advisable to run the driver in its own runtime or thread. On Windows it has to run in the helper of the user's desktop: the SYSTEM service does not see their clipboard.
