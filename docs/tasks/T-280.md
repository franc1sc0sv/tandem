# T-280 — Lost monitor report on the non-owner after pairing

Found by the acceptance agent (part B, round 5, `docs/reports/acceptance-2026-11-19-b5.md`), flows F3 ("apply successfully") and F4, screen P9 (`F-Transactions`).
`harness/` below is `docs/reports/acceptance/2026-11-19-b5/harness/`.

## What fails

Two real agents over loopback (`--sim-backends` host doubles), paired through the UI, then the same standard monitor plugged into both (`harness/t3.mjs`: Std-34 over DP on one machine and over HDMI on the other). Both agents agree that side `A` owns Std-34. In 3 of 7 fresh pairs checked right after setup (`r2`, `rp1`, `q2`), the agent on side `B` (the non-owner) has `report: null` for every monitor it shares, while the owner has a report (`harness/mon.mjs`):

```
m1 b  std-34  owner a  report null
m2 a  std-34  owner a  report { input: display_port, power_on: true, signal: true }
```

It stays that way for minutes (4 min on `r2`) until the owner reads a different input. Meanwhile, every scene applied from `B` fails at once:

```
WARN tandemd::agent: transaction failed: ShowMachine { monitor: "std-34-1dbde55e", machine: B } failed:
show machine B on monitor std-34-1dbde55e: it is not known which machine is shown (the real input,
or which input each machine goes to, is missing); without that it could not go back
```

- `r2`: 12 "Save and apply" and 12 card "Apply" from `B`'s window: all 24 failed, and the monitor never switched (`harness/t250.mjs`). The same scene applied from `A` worked at once. After that switch the owner sent a new report, and `B` worked again.
- `q2`: card "Apply" of "Only Mac" from `B`'s window. Changes in progress shows the failure above, and the bus does not move (`harness/t280b.mjs`).
- The other 4 pairs (`r3`, `r4`, `rp2`, `q1`) had the report on both sides. `r3` passed 24 of 24 runs from `B`.

## Likely cause

Both agents scan for monitors every 5 s and announce their channels in their capabilities, which go out up to 250 ms later (debounced). `MonitorDirectory` keeps **one** report per monitor id, tagged with the machine that read it, and `report()` only shows it while that machine is the owner:

1. `A` scans first. It does not know `B`'s channel yet, so it owns the monitor alone, reads it and sends `ControlMsg::Monitors`. `B` stores `(A, report)`.
2. `B` scans a few ms later, before `A`'s capabilities arrive. `B` does not know `A`'s channel, so `B` thinks it is the owner. It reads the monitor itself, and `set_report(B, …)` overwrites `A`'s report.
3. The capabilities cross. Both elect `A` (tie goes to `A`, DECISIONS T-110). `B` stops reading, and its stored report is tagged `B`, so `report()` hides it.
4. `A`'s reports did not change, so `MonitorHub::tick` never sends them again. `set_peer` only resends them on a new link.

The logs fit this order. In `r2` and `rp1` the owner logged "new monitor" 1-2 ms before `B`. In `r3`, where `B` logged first, the report was there. Owner-first does not always fail (`r4`), which matches a window of a few ms. `t280.mjs`, which adds the monitor on one side and then the other, did not reproduce it in 18 tries, because a monitor added later changes the owner's report list and that resends it.

## Expected fix

- The non-owner must not end up without the owner's last report. For example: keep one report per machine (not one per monitor), or have the owner resend its reports whenever the owner set it computes changes or the other's channels change.
- A test with the two directories in that order: `A` reports, then `B` reads while it still believes it is the owner, then the channels cross. `B` must show `A`'s report. The test fails before the fix.
- Optional: until it has the owner's report, a scene step from the non-owner could ask the owner for the current input instead of failing.

## Notes

Evidence: `docs/reports/acceptance-2026-11-19-b5.md`, section "New failure".

Cause confirmed as described above. `tandem_monitor::Directory` kept one report per monitor, so `B`'s own early reading (taken while it did not know `A`'s channel yet) replaced `A`'s; once both elected `A`, `report()` hid `B`'s reading and `A` never sent again because its reading did not change.

Fix:

- `Directory` keeps the last report per (monitor, machine) and shows only the owner's. When a machine stops owning a monitor (re-election on a change of channels), its report of that monitor is forgotten, so a stale one never comes back.
- `MonitorHub` sends its reports again on the next turn whenever the other's announced channels change (belt and braces: the other may have stored something else before it knew this machine's channels).
- Each `ControlMsg::Monitors` is the sender's whole list, so `Directory::set_reports` replaces everything that machine sent before (review of #183). A reading from a machine that never owned the monitor here (its early claim, or what it sends on a new link) is dropped as soon as it stops reading, instead of being shown later as current if that machine becomes the owner.
- No wire change, so `PROTOCOL_VERSION` stays at 41.

Tests (all fail without the fix): `directory::tests::an_early_reading_of_the_non_owner_does_not_replace_the_owners_report`, the property `both_show_the_owners_report_in_any_order` (every order of `A`'s report, `B`'s reading and the channels crossing, on both sides), `monitors::tests::the_owners_report_survives_an_early_claim_of_the_other` (two hubs driven through their own `tick`) and the two-agent `tandem-sim` test `an_early_claim_of_the_non_owner_does_not_hide_the_owners_report`, which injects the Mac's early claim after pairing and applies "Only Mac" from the Mac. Each was looped 60 times.

Real agents (`harness/` with `tandemd` and `acc_host` built from this branch, `--sim-backends`): 15 fresh macOS+Windows pairs set up with `setup.sh`, and `mon.mjs` showed the owner's report of every shared monitor on both sides on all of them (before: missing on side `B` in 3 of 7). `t250.mjs`, changed to drive the window of the non-owner (`B`), passed 10 "Save and apply" and 10 card "Apply" on 6 of those pairs (120 of 120 runs, the monitor switched every time). One more run stopped early because the UI build it served from was deleted mid-run; the pair was not counted.
