# T-190 — `pairing_hot_opens_the_input_session` is still flaky on macOS

## Context

Failure found by the acceptance agent, part C, round 2 (2026-11-18, `origin/develop` b3841bc). See `docs/reports/acceptance-2026-11-18-c2.md`.

## Failure

G11. T-160 (c049ae5) left the test with counter ports and an `until_pairing` that fails instantly, but the `develop` CI run at 97442ab (T-150, run 44368941401) went red again on `macos-latest`:

```
test pairing_hot_opens_the_input_session ... FAILED
thread 'pairing_hot_opens_the_input_session' panicked at crates/tandemd/tests/pairing.rs:38:10:
the test exceeded the maximum time: Elapsed(())
test result: FAILED. 6 passed; 1 failed; finished in 30.21s
```

It is the 30 s deadline of `within` (not a pairing failure): some wait in `pair_two_fresh_agents` does not finish on macOS. Locally it passes (two runs of `cargo test --workspace`, 1465 tests, and 6 consecutive runs of `--test pairing`).

## Expected fix

- Find out which wait hangs (`until_input(... session)`, `desk.wait_for` of the name, or the exchange of announcements) by adding to `within` a label that says which, and reproduce the race (loop of 200 runs under load).
- Fix the cause (waits on events, not deadlines); do not raise the deadline nor use `#[ignore]`.
- Make the timeout message say what was awaited.

## Notes

Status (2026-11-18): **blocked for lack of reproduction**; the cause was not found and no fix was improvised.

Done:
- `within` now has the variant `within_for(label, ..)` and `until_input` takes a label: on expiry, the panic says what was awaited (Mac or PC input session, names on the desk). The next CI failure will say which wait hangs.

Ruled out (with evidence):
- Locally on Linux: 70 runs of `pairing_hot_opens_the_input_session` and 25 of the full `pairing` binary, with 6 to 12 `yes` processes competing and pinned to 1 or 2 CPUs (`taskset`): 0 failures.
- macOS CI on this branch: the test repeated 50 times inside a single run (2 side orders x 25) passed (run 44383150444).
- Race "capabilities announcement ignored before `adopt_side`": the side change happens before saving the trust (`pairing.rs`) and the normal endpoint does not accept the other one until then; there is no window.
- Pairing attempt lost on a still-closed port (without ICMP, as on macOS): with a port that swallows packets the other one is found in ~1 s.

Unconfirmed suspicion: QUIC startups in debug with scarce CPU on macOS that exceed the link manager's `connect_timeout` (1 s) or the test's `heartbeat_timeout` (1.5 s). Resume with the expiry label when it fails again.

Update (2026-11-19, T-230): **superseded by T-230**. The cause is still not proven, so this stays `blocked` until a labeled failure appears.
- Every `within` in `crates/tandemd/tests` (including the unlabeled one in `pairing.rs`, line 38 in the macOS failure) now reports the call-site line when it expires (`#[track_caller]`), so the next failure names the exact wait.
- The suspicion above (link timings too tight for a slow runner) is what T-195 relaxed (`common::health()`: 5 s connect, 2 s ping), and `pairing.rs` already uses it.
- T-230 found a different, proven race in the drag tests (a request delivered before its handler registers) and fixed it. The pairing flow has no equivalent spawned handler.
- Run 44442801041: the whole `tandemd` test suite ran 20 times on each of macOS, Ubuntu and Windows with 0 failures, including `pairing_hot_opens_the_input_session`.

Update (2026-11-19, T-291): **done, superseded by T-291**. The labeled failure appeared (run 44576241294: "waiting for: input session open on Mac"), and T-291 found and fixed the cause. Each side saves trust on its own once both codes are confirmed. When the side that switches takes more than `CLOSE_WAIT` to save, the other side dials first and is rejected, and since T-152 a rejection meant "forgotten", so it unpaired for good. The "no window" claim above held only while both saves finished within `CLOSE_WAIT`. Details, the fix and the deterministic test are in `docs/tasks/T-291.md`.
