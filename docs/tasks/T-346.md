# T-346 — The Mac reads the monitor directly

## Context

Confirmed on real hardware on 2026-11-19: with the 34" on HDMI, the Mac's `monitor-ddc` (`IOAVService`) gets a DDC channel, the firmware answers the probe (`0xEA`), and the Mac computes the same monitor id as the PC. The election then makes the PC the owner (lower latency, or `A` on a tie, DECISIONS T-110), and the Mac only learns the monitor's state through the PC. The user wants the Mac to know the monitor's real state by itself whenever it can.

## Scope

1. A machine that has a channel but is not the owner reads the live state itself (read-only `Get 0x60` and `0xEE`, never the event cursor, which stays with the owner): the UI on that machine uses its own reading when it is fresher than the owner's report.
2. When the owner leaves (PC off, link lost), the other machine with a channel takes over at once, without waiting for the next scan, and the event cursor carries on from the last event the old owner reported.
3. The Mac can switch the 34" itself (Set `0x60` with the firmware verdict) while it has a channel and the PC is unreachable.
4. DESIGN §10 and DECISIONS (refines T-110) describe it.

## Acceptance criteria

- [x] Tests: the non-owner with a channel reads live state and never reads events; owner loss hands over to it within one poll; switch from the Mac with the PC off.
- [x] DESIGN §10 and DECISIONS (refining T-110) describe it.
- [x] Quality gate and CI green.

## Pending hardware verification

- [ ] With the 34" on the Mac and the PC off, the Mac shows the real input and can switch it.
- [ ] The Mac's Monitors screen updates the input within 1 s of a switch made from the monitor's own buttons, while the 34" shows the Mac. With the PC on and reachable this now comes through the PC's report (see Notes): the PC polls every 1 s and then reads the event ring, which on the real 34" can push the report past 1 s.
- [ ] Windows (`dxva2`): whether `GetVCPFeatureAndVCPFeatureReply` rejects a reply whose echoed VCP code differs from the request, as the macOS backend does. If it does not, Tandem's own check of the direct reading (below) is the only guard on the PC when it is the non-owner.
- [ ] With the link to the PC cut and the PC still on (both hosts talking to the 34"), the Mac's direct reading never shows a wrong input, and the PC's own readings stay sane.

## Notes

**Adapted to the shared DDC/CI buffer (monitor-firmware PR #2, `docs/targets/lc34g55t/inactive-hdmi-ddc.md`).** The 34"'s DP and HDMI share one request buffer, one pending flag and one reply length, and the event cursor is global: if both machines talk at the same time, either can get the other's reply. Scope item 1 as written (the non-owner reads whenever it has a channel) would overlap the owner's traffic every second, so it was narrowed to the safe rule the brief allows:

- While the owner is reachable over the control plane, the non-owner sends nothing to the monitor. It shows the owner's report, as before. The scan probe (`Get 0xEA` every scan) predates this task and stays.
- While the owner is unreachable (no control link) but not yet given up for lost (`peer_lost_after_secs`), the non-owner reads `Get 0xEE`, `0x60`, `0xEE` on every poll, never an event register. It may also switch the input itself (`Set 0x60` + verdict, item 3). `MonitorHub::set_peer_reachable` follows the orchestrator's `peer_connected`.
- Every reply is validated. The backend drops a reply whose echoed code differs (`monitor-ddc` `wire::parse_vcp_reply` on macOS). On top of that, `tandem_monitor::local::live_agrees` keeps a direct reading only if both `0xEE` replies are equal, carry the DDC/CI-enabled flag (bit 6) and name the same input as `0x60`. Otherwise the reading is dropped and the previous one stays.
- The direct reading is shown over the owner's report (input, power, signal; the events stay the owner's) until the owner reports again or the owner changes.
- Item 2: a cut link alone still does not move the owner (T-110), because two owners would both drive the global event cursor. Once the owner is given up for lost or powered off by a plan, the hand-over happens in the same poll: `set_peer` wakes the loop and no scan is needed. The new owner starts from the cursor the old owner last reported. `MonitorReport::cursor` is protocol v45 (v43 and v44 went to T-345 and T-344). The cursor only moves with the events, so the report is not resent on every poll.

A time slot granted by the owner was rejected: it adds control messages to obtain the same `0xEE` the owner already reads and sends every second.

The sim now calls `Orchestrator::clear_peer` when the last link drops, as `tandemd::network` does. Before this change, `peer_connected` in the sim stayed `true` after a link loss. The sim's shared bus can also cross replies on purpose (`SimMonitors::cross_replies`), standing in for a backend that does not check the echoed code.

Seen but not changed (pre-existing since T-110): both machines still probe (`Get 0xEA`) on every scan. A probe that crosses with the owner's traffic could make the owner see a bad reply for one poll, or make a probe fail and flip that machine's channel until the next scan. A follow-up could let only the owner probe while the other machine is reachable.

Tests: `tandem-monitor` (`local.rs`: hand-over cursor, cursor that moves only with the events, direct reading of `0xEE`/`0x60` only, crossed replies dropped, a proptest on `live_agrees`, switch without being the owner; `directory.rs`: hand-over captured once, direct reading over the owner's report), `tandemd` (hub with two agents on one bus; `target_of` with the owner unreachable), `tandem-sim/tests/monitor_direct.rs` (two real agents on one shared bus: the non-owner only probes while the owner is reachable; with the PC unplugged the Mac reads the live state, switches with the verdict and, once the PC is lost, takes over within one poll from the PC's cursor; crossed replies never shown).
