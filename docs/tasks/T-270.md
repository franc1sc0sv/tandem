# T-270 — The locked "Allow remote execution" switch

## Context

Finding of the acceptance agent (part A, round 5, `docs/reports/acceptance-2026-11-19-a5.md`), rules G6 ("every interactive element does something real and verifiable in the agent; nothing decorative that looks like a button") and P3 (`V3-Machine`).

T-244 made the demo announce `switchable` exactly as the agent does (only `input` and `clipboard`, DECISIONS T-098). The "Allow remote execution" row on the other machine's page (`apps/tandem-ui/src/screens/Machine.svelte`, `section.envs`) stays a `Switch`, now with `locked`: it keeps the look of an enabled switch that is on, and clicking it or pressing Space does nothing. Measured with `docs/reports/acceptance/2026-11-19-a5/harness/switch.ts` (output in `docs/reports/acceptance/2026-11-19-a5/locked-switch/switch.txt`), on `mac-win` (both sides), `win-win`, `mac-mac` and the `peer-off`, `link-down` and `no-agent` trouble states:

- `role="switch"`, `aria-checked="true"`, `aria-readonly="true"`, `aria-disabled="true"`, native `disabled` false, `opacity: 1`, the same green track as the working Keyboard and mouse and Clipboard switches, `cursor: default`.
- After a click and after Space: still `aria-checked="true"`, no toast, no request. Nothing on screen tells the user why; the only explanation is the native tooltip ("Always on: remote execution can't be turned off from here.") on hover and a screen-reader-only text.
- The tooltip says "from here", but there is no other place: the agent never lets the Tunnels module be switched (`crates/tandemd/src/modules.rs`, `Tunnels` has the default `switchable() -> false`, `state()` is always `Active`).

Screenshots: app `docs/reports/acceptance/2026-11-19-a5/locked-switch/switch-mac-win.png` (and one per pair and state in the same folder); mockup `docs/mockups-png/V3-Machine.png` (the same switch, on). The pixels match the mockup (`machine-b` 99.99 % / 98.6 %), which is why the round-4 parity check cannot see it: the problem is that a control that looks operable is not.

It also leaves the decisions in conflict. DECISIONS T-115 says "Allow remote execution" is that machine's `tunnels` module switch and that "on this one's, the same module is turned off from its row"; DECISIONS T-098 says Tunnels has no switch. Since T-244 the code follows T-098 on the Modules list and neither on this row, and no entry in `docs/DECISIONS.md` or `mockups/README.md` ("What the mockups say and DECISIONS corrects") records the locked switch. `docs/tasks/T-244.md` mentions it only in its notes.

## Expected fix

Pick one and record it in `docs/DECISIONS.md` (superseding the T-115 line), so code, decisions and mockup agree:

- **Preferred:** drop the switch. Either remove the "Allow remote execution" row (the Modules list already shows Tunnels as a plain chip) or draw it as a status, like the other non-switchable modules (status chip "always on", no `role="switch"`). Add the difference to `mockups/README.md` with its region so the `machine-b` comparison masks only that row, as ACCEPTANCE allows.
- Or, if the product wants a real switch: make Tunnels switchable in the agent (T-098 changes: what turning it off stops, how it reaches the other machine), so the switch does something verifiable.

Either way, no visible control that cannot be operated, and no hint that points to "from here" when there is no other place.

- [x] `docs/DECISIONS.md` has an entry that settles T-098 vs T-115 for this row; `mockups/README.md` lists the difference if the row changes.
