# T-239 — `input-cross` on the PC: drive the edge through the agent

## Context

In the real cable test (develop `facf263`, the PC is side B, the Mac side A, USB4 link up and adopted, every tunnel check green both ways), the PC's `input-cross` check (`crates/tandem-hw`, covers H4 and T-093) failed after 24 s with `no edge crossed to the other machine with synthetic motion`: 6 s per edge, all four edges. The PC agent's log showed no input lines during the check. The Mac's own `input-cross` failed only because the PC agent had been restarted; that run is not part of this task.

## Root cause

The check pushes the cursor with `SendInput` (the `Emulator` of `tandem-input`), and the Windows capture throws away every injected event on purpose, as its loop guard:

- `Translator::push` (`crates/tandem-input/src/windows/capture/mod.rs`) returns early for hook events with `LLMHF_INJECTED` / `LLKHF_INJECTED`.
- `RawMotion::push` (`crates/tandem-input/src/windows/capture/mouse.rs`) drops Raw Input with `hDevice == 0`, which is what `SendInput` produces.
- Crossing needs `MotionRelative` (`ServerSession::handle_local`); on Windows only Raw Input gives it. The hook only gives `MotionAbsolute`, which is clamped to the desktop and never goes past an edge.

So synthetic motion on the PC never reached edge detection, whatever the arrangement. The check could not pass on Windows by design.

The other suspects were ruled out:

- **No screens or edge** ("side B, 0 screens declared"): with no `[[screens]]` in the desk, `input::screens::arrangement` uses the screens each agent reads and the default arrangement (A to the left of B). There is an edge: the PC's left one. Provisioning does not need to declare screens.
- **No input session on side B**: the check already fails early with `no input session with the other machine` when `InputStatus::session` is false, and it got past that point.

### The macOS side

The macOS capture (`TapContext::handle` in `crates/tandem-input/src/macos/capture/sys.rs`) only skips events whose `kCGEventSourceUserData` is `INJECTED_MARKER`. The emulator (`CgSink`) posts with a `HIDSystemState` source and never sets that field, so the check's `CGEventPost` motion goes through the tap like the real mouse and reaches the edge. Mac to PC does not have this problem, and the Mac check keeps covering the real tap.

## Fix

- New `UiCommand::SyntheticMotion { dx, dy }` (protocol v40): the agent sends the motion into its running capture sink, as if captured, so it goes through the real server session, geometry, link and the other machine's injection. It is accepted only when the agent's config has `[input] synthetic_motion = true`; otherwise it is rejected. A normal installation never writes that key, and the Windows capture filter is unchanged.
- `tandem-hw provision` writes `synthetic_motion = true` for the test agents.
- `input-cross` picks how to push with `Drive::for_os`: on Windows through the agent (`Drive::Agent`), on macOS through the system (`Drive::System`, unchanged). The result says which one it used.

## Notes

- On Windows the check no longer covers the low-level hook and Raw Input path: that path cannot be driven by injected input at all. It is covered by moving the real mouse (pending list below).
- Found while checking the macOS side: `CgSink` never sets `INJECTED_MARKER`, so the tap's echo guard is never triggered. When the Mac receives input, what Tandem injects reaches its own tap like local input (D7 arbitration observes it). This task does not change it, because setting the marker would also hide the check's motion from the tap. It needs its own task, verified on the Mac.
