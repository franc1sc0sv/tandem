# T-341 — No phantom display on the Mac

## Context

T-340 takes the 34"'s HDMI screen out of Tandem's input geometry while the 34" shows the PC. macOS still owns that display: the Mac's own trackpad and mouse walk into it, and windows open there unseen. The user wants this solved inside Tandem, with no external app (2026-11-19). Decision in `docs/DECISIONS.md` (T-341).

## Scope

1. A `DisplayPower` trait with a macOS backend that turns an external display off and on through `CGSConfigureDisplayEnabled` (private CoreGraphics API, resolved with `dlsym` like `monitor-ddc`'s `IOAVService`, so a macOS without it reports "unavailable" instead of failing), and a test double.
2. When the active scene (or the real input reported by the owner) says the monitor shows the other machine, the Mac turns that display off; when it shows the Mac again, it turns it back on **before** the input switch is reported done, so the user never sees a black monitor on the Mac's input.
3. Safety: the agent turns every display it turned off back on when it exits (normal exit, signal, panic hook) and at start-up (a display left off by a crash). The list of displays it turned off is saved in the state so a restart can undo it.
4. Windows: same trait, no-op backend (the PC's DP screen stays; Windows does not show a phantom because the PC owns the monitor's active input while it shows the PC). Re-check this on hardware and note it.
5. The "Monitors" module on the Mac page says whether display control is available.

## Acceptance criteria

- [x] Tests with the double: off when the scene moves the monitor away, on before the switch back is done, on at exit and at start-up after a crash.
- [x] A macOS without the symbol builds, runs, and reports display control as unavailable.
- [x] `unsafe` only in small FFI functions with `// SAFETY:`.
- [x] DESIGN §10 describes the behaviour; DECISIONS has the dated line.
- [x] Quality gate and CI green.

## Notes

- `DisplayPower` trait in `tandem_input::displays` (`FakeDisplayPower` double, `NoDisplayPower` for Windows); macOS backend in `tandem_input::macos::display_power`, the private call resolved with `dlsym` (RTLD_DEFAULT, then SkyLight), scope `kCGConfigureForSession`.
- The logic is `tandemd::displays::DisplayGuard`: follows `shows` (the owner's real input, the same the geometry uses), wakes before a switch with a 30 s hold, turns a display back on after 15 s of unknown input, never turns off the only screen or one that is not the last `screen-N` (it would renumber the others). It saves what it turned off in `displays-off.json` next to `state.json` (machine-local, so not in the shared `State`).
- Protocol v46: `Step::DisplayOn`. The switch is done by the monitor's owner (often the PC), so the orchestrating agent asks the machine whose input it is to light its display right before the `SwitchMonitor`; its failure never stops the switch.
- Tests: unit tests of the guard (off/on, wake and hold, exit, start-up after a crash, unknown-input grace, only/last screen, unavailable), the Monitors module line, and a two-agent sim test (`tandem-sim/tests/display_power.rs`) that checks the Mac's display goes on while the 34" still shows DP, asked from either machine and from a scene.
