# T-160 — Flaky tests in CI (macOS and Ubuntu)

## Context

Failure found by the acceptance agent, part C (2026-11-18, `origin/develop` 04f2967). See `docs/reports/acceptance-2026-11-18-c.md`.

## Failure

## Expected fix

For each one, reproduce the race (loop of 200 runs or `--test-threads=1` under load), first write the test that forces it to fail and fix the cause (clocks with `tokio::time::pause()`, waits on events instead of fixed deadlines, ephemeral ports). Do not raise deadlines nor mark `#[ignore]` to hide them.

## Acceptance criteria

- [x] Each of the three tests passes in a loop locally under load (see Notes). The 200 runs and the 20 on CI remain as ongoing verification: they are confirmed with the next `develop` runs.
- [x] None uses a real `sleep` nor fixed deadlines that depend on the machine's load (`docs/TESTING.md`).

## Notes

Causes and fixes:

- `latency_includes_the_wait_with_the_driver_busy`: it assumed that, 5 ms after sending the crossing, the driver was already inside `set_grab` (a 60 ms `sleep`) and demanded a sample of at least 40 ms. With the machine loaded the driver was slow to pick up the crossing: the movements got batched with it in the same batch, were sent before the wait and the sample came out almost zero. It also read the first sample and not the worst. Now the simulated capture signals that it is busy and waits for the test to release it; the test captures the movements only after the signal, releases it after `busy` (the `sleep` is a floor, it never lasts less) and waits until it sees a sample of at least 2/3 of `busy`. It does not depend on how fast the threads run.
- `an_mcp_client_opens_a_tunnel_runs_reads_copies_and_closes`: the macOS and Ubuntu failure (stderr `""`) was that `output` returned as soon as stdout arrived, and was read only once; T-131 already fixed it with batch reading with a cursor (it has not been seen red again since 04f2967). The Windows error (10013, "Address already in use") comes from the ports: `free_port()` asked the system for 0 and released it; Windows hands out ephemeral ports in order and reuses the one just released, so another test (or a QUIC client's source port) received it before the agent opened it. `test_ports::free_port()` and the new `free_pair()` now hand out ports from a process counter, below the ephemeral range and Hyper-V's, which are not repeated between tests; the retry of `start_pair!` remains for a clash with another process. `free_pair` moved from `tests/pairing.rs` to `test_ports` to share the counter.
- `pairing_hot_opens_the_input_session`: I could not reproduce it (neither on Linux with 12 `yes`, nor pinned to one CPU with 4, nor on the Mac with 40 `yes` and 10 processes in parallel: 0 failures in more than 300 runs), so I cannot state the cause. The CI log shows that the 30 s deadline (`within`) expires without saying at which step. What was fixed: `until_pairing` waited forever for a `Comparing` even if the agent had published `Failed`, and now the failure comes out immediately with its reason; and the ports can no longer clash with the ephemeral ones (same fix as above). If it turns red again, the message will say whether it was a pairing failure (for example, the pairing port `port + 1` taken) or a hang of the input engine after pairing.

Local runs with a load of 6 `yes` processes (each with its own test binary, 30 times):

| Test | Failures |
|---|---|
| `latency_includes_the_wait_with_the_driver_busy` | 0/30 |
| `an_mcp_client_opens_a_tunnel_runs_reads_copies_and_closes` | 0/30 |
