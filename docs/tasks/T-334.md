# T-334 — The agent logs why it terminates

## Context

Found with T-333 on a real Mac with v0.3.0: the agent disappeared after System Settings' "Quit & Reopen" and `tandemd.log` said nothing. Only the unified log (`Handling Quit AppleEvent`, `launchd: termination reported (0, 0, 0)`) showed what happened.

## Failure

Several ends of the process left no line in `tandemd.log`:

- the orderly shutdown wrote "shutting down", but not what started it (SIGTERM, Ctrl+C, the Windows console closing, the system shutting down);
- on macOS the agent's thread ends the process with `std::process::exit` (`main.rs`, `run_hosted`), so nothing after `run` was logged with the exit code;
- a panic of the agent's thread went only to stderr (default panic hook), which the LaunchAgent does not keep, and then `ExitOnPanic` called `exit(1)` silently;
- AppKit's own termination (`exit(0)` after `applicationShouldTerminate:`) logged nothing.

## Expected fix

- `shutdown_signal` returns the reason, and `serve` / the shutdown line say it.
- Every exit path writes `tandemd exiting with code N: <why>` before the process ends, and the line reaches the file before `exit`.
- Panics go to the log.
- AppKit's termination at the end of the session (T-333's delegate) writes the same line.

## Acceptance criteria

- [x] `daemon::ShutdownReason`; `shutdown_signal()` returns it; `daemon::run_until` and `Daemon::serve` return it; the line is `shutting down (SIGTERM)` etc.
- [x] `tandemd::exit::Exit` formats and logs `tandemd exiting with code N: <why>` for a stop, an error, a panic and AppKit's termination; `main.rs` logs it before every `process::exit` and before returning from `main`.
- [x] `logging::log_panics` sends panics to the log.
- [x] Failing tests first, including a test with the compiled binary that reads the line from `tandemd.log` after the process has exited.
- [x] Quality gate and CI green.

## Pending hardware verification

- [ ] With the installed app: `launchctl bootout gui/$(id -u)/<label>` (or `kill -TERM <pid>`): `tandemd.log` ends with `shutting down (SIGTERM)`, `state saved at …` and `tandemd exiting with code 0: stopped by SIGTERM`.
- [ ] Log out and back in: if loginwindow sends the Quit Apple event, the log ends with `tandemd exiting with code 0: AppKit terminates it for log out`; otherwise with the SIGTERM line above.
- [ ] A failed start (for example a broken `tandem.toml`): the log ends with `tandemd exiting with code 1: error: …` and launchd restarts the agent (`KeepAlive`).

## Notes

- Stacked on T-333 (#199): the AppKit line is written from T-333's delegate, so `run_app_loop` takes an `on_session_end` callback that `main.rs` gives as `Exit::SessionEnd(..).log()`. Merge T-333 first. This branch then only adds its own commit.
- Failing first: `tests/exit_log.rs::a_failed_start_logs_the_exit_code_before_exiting` failed on the T-333 code. The log's last line was the multi-line TOML error and there was no exit line. The unit tests (`exit::tests::*`, `daemon::tests::run_returns_the_reason_its_shutdown_gave`, `a_shutdown_that_only_says_stop_is_requested`, `the_shutdown_reason_reads_well_in_the_log`, `sigterm_is_reported_by_shutdown_signal`) did not compile before the change: the API they call did not exist.
- Flush: `logging.rs` does not use `tracing_appender::non_blocking`. The file layer writes each event with one `write` on a `Mutex<File>`: no buffer, no worker thread. So the line is in the kernel before `process::exit` and there is no guard to drop. The binary test checks this end to end on all three platforms. On macOS it goes through the agent thread's `process::exit(1)`.
- A multi-line error is joined onto one line in the exit line, so the exit stays the log's last line. The full error is still logged just before it.
- `shutdown_signal()` now registers SIGTERM (and the Windows console handlers) when it is called, not on the first poll. The test needs this to signal its own process safely: the handler has to be installed before `kill` runs. In the agent the call sits right before the IPC bind: after the rebase on T-341…T-346 the binary test sent SIGTERM as soon as `IPC listening` was logged, while `daemon::start` was still running, and the default action killed the process (no exit code). Registered before the bind, a stop sent once the agent is reachable always goes through the orderly shutdown.
- `daemon::run` keeps its old signature (`shutdown: Future<Output = ()>`, returns `()`) for the UI's and the CLI's tests. `run_until` is the version that returns the reason. A future returning `()` maps to `ShutdownReason::Requested`.
- `sigterm_logs_the_reason_and_the_exit` (binary, real SIGTERM) runs on Linux only, like `two_processes.rs`: on macOS the temporary path is too long for the IPC socket. On the development Mac, an unbundled debug `tandemd --sim-backends` was checked by hand. After `kill -TERM` the log ended with `shutting down (SIGTERM)` / `state saved` / `tandemd exiting with code 0: stopped by SIGTERM` (exit code 0). A Quit Apple event with reason `'shut'` gave `Quit AppleEvent for shut down` followed by `tandemd exiting with code 0: AppKit terminates it for shut down`.
- Rebased on T-341: `Daemon::serve` still turns the displays back on after `run_until`, and the panic hook of `start_displays` still runs `restore_on_panic` (it wraps `log_panics`). AppKit's exit at the end of the session skips both, so `start_displays` registers the guard and the session-end callback calls `displays::restore_at_process_exit` before the exit line (test `the_process_exit_outside_the_agent_turns_the_displays_on`).
- Out of scope: the Windows service paths (`--service`, `--input-helper`) keep their own logging. This task covers the agent (`tandemd` with no subcommand).
