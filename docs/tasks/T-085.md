# T-085 — Real initial state of the desk

## Context

Monitors do not report their input (docs/research: the 34" always reads `0x09`; the 32" does not update `0x60` after a change from the menu) and each system sees the ghost monitor as active, so the real state (which machine each monitor shows) cannot be detected alone. In the real test the app showed an invented state.

## Scope

1. **"Unconfirmed" state:** when there is no saved state, or it was restored from an earlier startup and something may have changed by hand (another session, a change from the monitor's menu), the desk is marked as unconfirmed.
2. **Main path, exact and without asking: "Apply mode".** With the state unconfirmed, the UI offers to choose Mac only / Shared / Windows only and Tandem sends each monitor over DDC where it belongs (verified profiles); when it finishes the state is confirmed without asking anything. It needs the machine with DDC (today the PC) to be on and linked; if not, path 3 is offered.
3. **Flicker-free alternative:** the UI asks once, visually and quickly: for each monitor, "what does it show now?" with two buttons with the name of each machine (and "nothing / black"). The user answers on either machine and it is synced.
4. **Correction at any time:** in the scene, a gesture or menu on the monitor "it actually shows the PC / the Mac" that corrects the state without sending DDC.
5. **Optional hint to preselect the answer:** if one machine has the monitor on its desktop and the other does not, or the topology indicates it, it is suggested, but the user confirms.
6. While the state is not confirmed, normal mode changes do not plan over an invented state: the first change works as "Apply mode" (sends all inputs, not only those that would change).
7. The PC's card does not show the built-in screen control (the PC has none); only a machine with a built-in screen in its capabilities (T-084).
8. Leave a pending item noted in `docs/research/`: test with the user whether the timing report (VCP/GetTimingReport) of the 32" SAM7489 distinguishes the input it shows (it does not work on the 34"); if it does, it would be an "input detection" capability per profile.

## Acceptance criteria

- [x] Startup without state: the UI offers "Apply mode" and the answering alternative; after "Apply mode" with simulated monitors, the state is confirmed and matches what was sent over DDC (frontend, agent and tandem-sim tests).
- [x] The first mode change with an unconfirmed state sends all inputs (test).
- [x] Correcting a monitor from the scene changes the state with no DDC step and is replicated to the peer (test with two agents).
- [x] Screenshots in the PR (demo mode).

## Notes

- **Core** (`tandem-core`): `State.doubt: BTreeMap<MonitorId, Doubt>` with `Doubt::{Unknown, Stale, Blank}` (never known / from an earlier startup / the user said "nothing, black"). `State::initial` marks everything `Unknown`; `State::forget` (when the agent starts) turns what was known into `Stale`; `is_confirmed()` = no `Unknown`/`Stale` (a black monitor counts as known: it is not asked again). An earlier `state.json` without the field is read as confirmed, but the agent forgets it anyway at startup. An applied `SwitchInput` removes the monitor's doubt; a rollback leaves the doubts as they were.
- **Plans:** `Plan::to_mode` sends the input to every monitor in doubt even if it already seems to be where it should go (point 6), with `Attach` on the target machine and `Detach` on the other (it is not known what each desktop has). `Plan::apply_mode` does the same with all monitors, confirmed or not. `Plan::follow(cfg, before, after)` is the correction: no `SwitchInput` or power, only desktops (of the monitors that changed owner or were in doubt), built-in screen and geometry. What is forced is per monitor: if the user confirmed one, the first change only sends those still in doubt; from a startup with no state it is all of them.
- **Protocol v11:** `UiCommand::ApplyMode(Mode)`, `UiCommand::SetShown(BTreeMap<MonitorId, Option<Machine>>)` (`None` = nothing), the `doubt` field of `State` and `MonitorCaps.seen` (detected at startup). The correction runs as a transaction (`Agent::set_shown` → `start_txn`), so the final state reaches the other machine through the usual `ControlMsg::State` and it is rejected while another change is in progress; a monitor that is not wired to the named machine is rejected.
- **UI:** with the state unconfirmed, monitors are drawn with "?" and "unconfirmed", no mode appears chosen and choosing one (cards, tray) requests `apply_mode`. A floating notice next to the modes explains and offers "Say what it shows"; if the machine that switches the inputs is not on and linked (`applyReady`), the question appears directly, with a preselected hint (`hintFor`: wired to only one, the other off, only one detected it, or the last thing known). Each monitor has a "⋯" button with "It actually shows: the Mac / the PC / nothing". The built-in screen selector only appears on the card of the machine that announces it in its capabilities (without the Mac's announcement the laptop is drawn, without control); the PC never has it. The tray menu says "unconfirmed monitors" and marks no mode.
- **Demo mode:** `/?demo&fresh` (no state, PC off: direct question), `&pc=on` (also "Apply mode"), `&fresh=stale` (the last thing known as a hint).
- **Tests:** core properties with the physical truth different from what `State` believes for the monitors in doubt (`plan_reaches_mode` ends confirmed and in the requested assignment; `apply_mode_switches_every_monitor_and_confirms`; `following_a_correction_never_switches_an_input`); unit tests of `plan`/`state`/`store`; of the agent (`apply_mode_sends_every_input_and_leaves_the_state_confirmed`, `the_first_mode_change_with_an_unconfirmed_state_sends_every_input`, `saying_what_a_monitor_shows_corrects_the_state_without_switching`); `tandem-sim/tests/initial_state.rs` (apply without state from the Mac and from the PC, first change, correct from the PC without DDC writes and the Mac catches up, answer with "nothing"), with `DeskBuilder::unconfirmed` and `World::switch_by_hand` (the monitor's menu); frontend `confirm.test.ts` (includes the end-to-end demo: apply and answer).
- Other tasks' tests that measure exact steps start from a confirmed state (`State::confirmed`): the simulation confirms the main machine's except with `unconfirmed()`.
- "Apply mode" also sends the input a monitor is already on: on the 34" that re-syncs (~1–2 s black, docs/research/ddc-34-LC34G55T.md). That is why the flicker-free path exists.
- Out of scope: on reconnecting, a freshly started agent (unconfirmed) does not adopt the other's confirmed state; each UI shows its own until the first change or answer, which reaches both.
- Environment: in WSL, outside the sandbox, `pairing::tests::nobody_confirming_times_out_without_saving` also fails on `develop` (`ConnectionLost(TimedOut)` in 0.06 s); it passes in CI. It is not this task's.
