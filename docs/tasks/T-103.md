# T-103 — Tunnels: protocol and sessions

## Context

DECISIONS D8, D9, A7; DESIGN §8. Foundation of T-104…T-108.

## Scope

1. New `tandem-tunnel` crate (portable, no platform code). `Tunnel { id, title, project: Option<Project { name, root }>, origin: Machine, target: Machine, opened_by: Client { kind: Mcp|Cli, session }, state: Open|Closed, created }`.
2. New messages in `tandem-proto`: open and close a tunnel, list, and a data channel per tunnel (data-priority stream, T-101). The protocol version goes up.
3. **Survive the link:** the state lives in the target agent; each output flow carries a sequence number per byte; on reconnecting (over the same or another path) the origin asks "from byte N" and nothing is lost or duplicated. Circular output buffer per process (8 MiB by default) with a notice if anything was discarded.
4. Local IPC for clients (`tandem` CLI / `tandem mcp`): authentication through the user's IPC channel (DESIGN §11).
5. Tunnel state for the UI (`UiEvent::Tunnels`), grouped by project, read-only.

## Acceptance criteria

- [x] Two-agent scenarios: open a tunnel, cut the path in the middle of a flow, reconnect over another path and verify that the output arrives complete and in order (property test over cut points) (`tandem-tunnel/tests/survive.rs::the_output_arrives_complete_with_cuts_at_any_point`, with in-memory paths; `tandemd/tests/tunnels.rs`, with real QUIC over loopback and two connections).
- [x] Closing the tunnel from the origin closes its resources on the target (`survive.rs::closing_from_the_origin_releases_the_resources_on_the_destination` and `tandemd/tests/tunnels.rs`).
- [x] Quality gate and CI green (gate in WSL; CI in the PR).

## Notes

Done:

- `tandem-proto::tunnel` (the wire types, like `env` with T-105): `Tunnel { id, title, project, origin, target, opened_by: Client { kind: Mcp|Cli, session }, state, created }`, `TunnelUp` (`Open`, `Close`, `List`, `Attach { tunnel, from: [(flow, byte)] }`), `TunnelDown` (responses and, over the data channel, `Flow`, `Data { offset }`, `Lost { from, to }`, `End`, `TunnelClosed`), `ProjectTunnels` and `group_by_project`. New channel `Channel::Tunnel`, greeting `Peer::Client(kind)`, `UiCommand::{OpenTunnel, CloseTunnel, GetTunnels}`, `Reply::{Tunnel, Tunnels}` and `AgentToUi::Tunnels` (the task's "`UiEvent::Tunnels`"). Protocol v25 (after T-100, v23, and T-093, v24).
- `tandem-tunnel` crate (portable):
  - `OutputBuffer`: circular buffer (8 MiB per flow by default) with absolute position per byte; `read(from)` gives the data, `Lost` if it was already discarded, or `Pending`; `accept(offset, bytes)` discards what is repeated.
  - `Host` (target): tunnel registry (opening is idempotent by id), `HostTunnel::add_flow` → `FlowWriter` and `add_resource(Box<dyn Resource>)`; closing releases the resources and ends the flows; closed ones are remembered for 10 min. `serve` handles a stream: a request, or the data channel (`Attach`), which moves to data priority (`TargetWire::start_data`) and sends a piece per flow per round, with `End` and `TunnelClosed` only when everything has gone out.
  - `Origin`: opens (random id), closes and lists over the active link (`set_link`); one follower per tunnel keeps the data channel and asks for it again from what it already has if the stream is cut or the link changes path. Mirror per flow to read the output (`read`, `flows`, `subscribe_output`), with what was lost counted and reported in the log.
  - Review of #84: the origin forgets closed tunnels after `OriginOptions::linger` (10 min; `survive.rs::the_origin_forgets_closed_tunnels_after_a_while`), and if an `Open` is left without a response (`Timeout`/`Wire`) it sends `Close(id)` in the background over each link that appears, so as not to leave an orphan tunnel on the target (`survive.rs::an_unanswered_open_does_not_leave_an_orphan_tunnel_on_the_destination`).
  - `Tunnels` (both sides) with `view()` for the UI: only the open ones, grouped by project.
  - `mem::MemPath`: in-memory paths that are cut now or after N bytes, for the tests.
- `tandemd::tunnels`: `QuicDialer` and the target side over QUIC (`ControlStream::into_data` with the connection's `Qos`, T-101); `peer::serve_stream` handles `Channel::Tunnel`; `follow_link` carries each new active link to the origin (started by `daemon`); `handle`: open and close only from a `Peer::Client` (the IPC only lets the user in, DESIGN §11), the UI receives `Rejected` (D9) and can ask for `GetTunnels` and receives `AgentToUi::Tunnels` with each change. With no title, the project's. `IpcClient::handshake_as` for the clients.

For the following tasks:

The new requests (`exec`, `kill`) enter as variants of `TunnelUp`/`TunnelDown` and of `UiCommand`.
