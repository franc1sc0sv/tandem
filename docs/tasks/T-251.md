# T-251 — The Updates pane loses the "Update all" step

Found by the acceptance agent (part B, round 4, `docs/reports/acceptance-2026-11-19-b4.md`), flow F13 ("plan to update both machines"), screen P11 (`F-Settings`, Updates tab).

## What fails

Two real agents, the app core with a test `latest.json` that offers 0.2.0 (`docs/reports/acceptance/2026-11-19-b4/harness/upd2.mjs`, `upd3.mjs`, `f13u.mjs`):

1. Settings → Updates → "Check now" finds 0.2.0. "Update all".
2. The other agent logs `the other machine asks to install a new version version=0.2.0`. The app core moves to `step = "ask_peer"` and then `"wait_peer"`, and `update_get` keeps answering `"step":"wait_peer"` for the 20 s the run waits.
3. The pane never shows "Asking the other machine to update…" or "The other machine is updating; …". For the whole 20 s it keeps the idle text "It installs on every machine, one at a time, without cutting the keyboard." (3 of 3 runs).
4. "Update all" stays enabled. Pressing it again gives the toast "an update is already in progress" and a console error (the rejected command).
5. After 20 s the run ends and the pane does show "the other machine did not come back".

The ui-update events the window receives, in order (same millisecond): `step: null` (busy taken), `step: "ask_peer"`, `step: "wait_peer"`. The `update_all` reply carries the view taken before the run started (`step: null`).

## Cause

`apps/tandem-ui/src/screens/Updates.svelte`, `updateAll()`: `view = await store.updateAll()`. The reply is the view from before the spawned run (`updater.rs`, `update_all` returns `view` captured before `spawn`). The step events of the run reach the window first and the late reply overwrites them, so `view.step` goes back to `null` until the next event, which only comes when the run ends. `disabled={view.step !== null}` then leaves the button enabled.

## Expected fix

- The pane must not let the command reply overwrite a newer view (for example: do not assign the `update_all` reply when an event already arrived, or give the views a sequence number and keep the newest). The same applies to `checkUpdates` and `setAutoUpdate`.
- A component or store test that delivers the step event before the command reply and checks that the step text is shown and "Update all" is disabled; it fails before the fix.
