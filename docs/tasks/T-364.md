# T-364 — A flapping USB4 link stops restarting the input session

## Context

Real desk, 2026-11-26, Tandem 1.0.1. The PC's `USB4(TM) P2P Network Adapter` kept disappearing and coming back (its interface index went through 13, 14, 20, 22 and 38). Its pings timed out about 50 times an hour. Each time the link manager moved to Wi-Fi and, 3 s after USB4 answered again, back to USB4. Each switch restarts the input session, so one short drop cost two restarts, and in one case the mouse was gone for about 13 s. The user saw a phantom mouse that "works only sometimes".

## Scope

- `LinkTable`: keeps a count of each link's recent drops, kept across its interface going away and coming back. The steady time before going back to a link that dropped is `settle` (3 s), doubled for each further drop within `FLAP_WINDOW` (30 min), at most `MAX_SETTLE` (10 min). Drops further apart start over at `settle`.
- DESIGN §6 (health and path switching).

Out of scope: keeping the input session alive across a switch, and the adapter's own drops on Windows (driver or cable).

## Acceptance criteria

- [x] Test: a link that drops five times waits 3, 6, 12, 24 and 48 s before it is chosen again, and is never chosen sooner.
- [x] Test: the wait is capped at `MAX_SETTLE` and goes back to `settle` after a quiet `FLAP_WINDOW`.
- [x] Test: the count survives the interface being removed and added again, also when the pings failed before the interface went away, and the link is not chosen before its wait.
- [x] The table property test and the manager's flicker test hold with the per-link wait.
- [x] Quality gate.

## Pending hardware verification

- [ ] With the USB4 adapter dropping on the PC: after a few drops, the input stays on Wi-Fi and the log shows far fewer "active link changed" lines per hour.
- [ ] With a steady USB4 cable: the first switch back still happens after 3 s.
