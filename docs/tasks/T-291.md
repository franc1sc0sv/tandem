# T-291 — A rejection right after pairing unpairs for good

Supersedes T-190, which stayed `blocked` without a reproduction.

## Failure

`pairing_hot_opens_the_input_session` (`crates/tandemd/tests/pairing.rs`) failed again on `macos-latest` in CI: run 44576241294, attempt 1 (PR #184, `develop` 53bdcb9). The labels from T-230 name the wait that hung:

```
test pairing_hot_opens_the_input_session ... FAILED
thread 'pairing_hot_opens_the_input_session' panicked at crates/tandemd/tests/pairing.rs:52:19:
the test exceeded the maximum time waiting for: input session open on Mac
test result: FAILED. 9 passed; 1 failed; finished in 30.24s
```

The test took 30.24 s in total, so the first pass hung: seeds (90, 91). There the Mac has the lower key, so it stays `A` and is the server, and the PC switches to `B`.

## Expected fix

- Find the event the Mac's input session waits for that never comes. Suspects: a link adopted from the other agent's connection (T-237), a peer set before the engine is ready, or a notice that is lost and never replayed (as in T-240).
- Force the ordering with a deterministic test that fails before the fix.
- Fix the cause in the daemon. Do not just raise the timeout.

## Notes

Cause (proven by forcing the ordering): the two sides save trust independently once both codes are confirmed, and nothing makes the other side's save happen before this side's first dial. `pairing::compare` only keeps the side that finished first waiting in `drain` until the other closes its stream, for at most `CLOSE_WAIT` (2 s). The PC (the side that switches) does more work before it saves: `adopt_side` rewrites the config, state and desk, and the input engine restarts. If that takes longer than 2 s on a loaded runner, the Mac follows the PC, dials it, and the PC's normal endpoint rejects the Mac's key because the PC does not trust it yet. Since T-152, `AgentProber` reads any key rejection as "the other machine no longer trusts this one" and calls `forget`. The Mac ends up `Unpaired` for good, no link comes up, and its input session never opens. That is the hang in the CI log. When the PC dials later, it is rejected in turn and unpairs too. With a 2.5 s delay injected before the PC's trust save (a local experiment, not committed), the test fails on every run with exactly the CI message. With the fix, the same delay passes.

Fix (`crates/tandemd/src/network.rs`): `PeerSide` carries a `Settled` that decides whether a rejection means "forgotten":

- A peer loaded from trust on disk at startup: yes, right away, as before (T-152; `a_peer_that_still_trusts_us_unpairs_when_rejected_on_reconnect` still passes).
- A peer just paired here: only once the other agent has accepted this side once (a connection this side dialled or adopted, or one the other side opened to this side). Until then the link manager keeps retrying, and the first dial after the other side saves trust links up.
- A safety net: if the other side never accepts within `PAIRING_SETTLE` (60 s) after pairing, it most likely failed to save trust. The rejection then counts as forgotten, so both sides end up unpaired instead of one waiting forever. This is not a timeout in the race: it only matters when the other side never saves.

The suspects in the task were checked and ruled out for this failure: a link adopted from an inbound connection and serving streams on any connection (T-237) do not change who rejects whom, and `set_peer` replays everything on each new link (T-240).

Tests:

- `a_rejection_before_the_other_saves_the_pairing_does_not_unpair` (`tests/pairing.rs`). The test plays the PC: it runs the PC's half of the pairing through `pairing::run`. The PC's normal endpoint is a stand-in whose trust rejects every key and counts the rejections. The test waits for the Mac to dial a second time after being rejected (it does not wait on a timer), checks that the Mac still trusts the PC, then starts the real PC agent, which now trusts the Mac, on the same port. It waits for the Mac to reach `Paired { link: Some(Usb4) }`. Before the fix it fails every time with "waiting for: the Mac dialling the PC again after a rejection".
- `network::tests::a_rejection_means_forgotten_only_once_the_pairing_settled`: the decision table of `Settled`.

Local loop (Linux, debug): the whole `pairing` binary 200 times with the default test threads and 100 times with `--test-threads=1`, all with no failures. Before the fix, the same loops (300 runs of the hot test, and 80 more with either side unable to dial) did not reproduce the failure without the injected delay, which matches how rare it is in CI.
