# T-110 — Monitors in Tandem

## Context

DECISIONS D11, D13; DESIGN §10; mockup `V3-Monitors`. Replaces T-095 and T-088.

## Scope

1. `tandem-monitor` crate: uses `monitor-ddc` (git dependency pinned by commit, declared in `[workspace.dependencies]`).
2. Each agent announces which monitors it sees with a live channel (in `Capabilities`). Owner election per monitor (DESIGN §10), deterministic on both machines; re-election when the channel is lost or the owner leaves.
3. Only the owner reads events and state; it distributes them to the other over the control plane. The other machine asks the owner for changes.
4. Orchestrator step `SwitchMonitor { monitor, input }` with verdict, maximum time and rollback.
5. IPC for the UI: monitors (compatible or not, real input, owner, latest events with time and icon), switch input.
6. **Automatic-return guard** for hardware tests: a utility that records the original input and restores it on finishing or if the process dies (separate watchdog process).

## Acceptance criteria

- [x] `tandem-sim` scenarios with two fake monitors (one standard, one factory): owner election, switch with verdict, re-election when the owner powers off, the factory one never receives a Set.

## Notes

- `tandem-monitor` (new crate): `election` (deterministic owner: the one with a compatible channel; with both, the one with the lowest probe latency with a 10 ms margin, tie to `A`; the latency is measured when the channel opens and does not change while it stays alive, so it does not oscillate), `directory` (channels of both, owners, owner reports, views for the UI), `local` (probe, `set_owned` with a new cursor for each owner change, reading of events and state, switch with verdict), `ring` (wrap-around of the `0xEF` clock at ~497 days without taking it for a restart; events' time with their 24 bits) and `guard` (automatic return: `InputGuard` in the process and the `tandem-monitor-guard` binary, which restores if standard input is closed without `disarm`).
- Protocol v19 (T-099 took v18): `MonitorChannel` with compatibility and latency; `ControlMsg::Monitors` (owner reports); `Step::SwitchMonitor`; `UiCommand::{GetMonitors, SwitchMonitor}`, `Reply::Monitors`, `AgentToUi::Monitors`.
- Orchestrator: `SwitchMonitor` goes to the owner (`MonitorControl`), with a maximum time of 20 s (the verdict is awaited for 12 s). New rollback in `tandem_core::run` (`Executor::undo`): if a later step fails, or the switch is left without a verdict, it returns to the earlier input; a `switch-failed` verdict is not undone (the firmware already stayed where it was). Power is still not undone.
- The other machine counts for the election while the state considers it on: when it powers off (or is lost, `peer_lost_after_secs`) its monitors pass to this one.
- The "Monitors" module is active with a DDC bus and "No DDC channel on this machine" without it (Linux, or if `monitor_ddc::system_bus` fails).
- The UI's Monitors screen is not part of this task: the Tauri session receives `AgentToUi::Monitors` and for now does not show it.
- Review of #80:
  - On Windows and macOS each enumeration gives monitors new numbers. The probe recognizes them by id and compatibility, and keeps the latency, the cursor and the events; it only redoes the connection.
  - The automatic return (guard and watchdog) waits for the verdict of a pending `ddc-switch-request`, up to 12 s, before comparing the input.
  - The hardware test disarms the watchdog only if the return was confirmed.
  - A `SwitchMonitor` without the current input known is rejected (`UNKNOWN_INPUT`).
