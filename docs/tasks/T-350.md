# T-350 — Opening Tandem when only the agent is running

## Context

Seen on the real desk on 2026-11-20, right after a clean install of v0.3.1 on the Mac
(remove `Tandem.app`, copy the new one, the LaunchAgent starts `tandemd`):

- Only `/Applications/Tandem.app/Contents/MacOS/tandemd` was running; `tandem-ui` was not.
- macOS showed "Tandem" as open (Dock / Force Quit / app switcher), with no window.
- Opening Tandem again (Finder, Launchpad, `open -a Tandem`) brought nothing up.
- Quitting it did nothing. The unified log shows the T-333 answer:
  `applicationShouldTerminate: NSTerminateCancel` / `App termination canceled`.
- Workaround: `open -n /Applications/Tandem.app` or running `Contents/MacOS/tandem-ui` directly.

Cause: `tandemd` lives in `Tandem.app/Contents/MacOS` and runs `NSApplication.run` for the drags
(T-121, `crates/tandem-files/src/drag_macos.rs`), so LaunchServices registers it as *the*
running instance of `com.franc1sc0sv.tandem`. Opening the app then only sends the reopen/activate
Apple event to that instance (the agent, which has no window, `Accessory` policy) instead of
launching the bundle's executable (`tandem-ui`). Its Quit is ignored on purpose (T-333).

## Goal

With only the agent running, opening Tandem the usual ways (double click in Finder or
Launchpad, `open -a Tandem`, `open /Applications/Tandem.app`, Dock) shows the main window,
and Quit from the Dock/app menu of that visible app quits the UI. The agent's T-333 behaviour
(ignore Quit, stop only through launchd or at session end) stays.

## Approach (keep the architecture; do not move `tandemd` out of the bundle)

Moving `tandemd` into its own nested bundle would give it a new code identity and make macOS
ask for Accessibility, Input Monitoring and Local Network again, against T-348. So:

1. In `drag_macos.rs`'s app delegate, handle the open/reopen paths (`kAEOpenApplication`
   `aevt/oapp`, `kAEReopenApplication` `aevt/rapp`, i.e. `applicationShouldHandleReopen:hasVisibleWindows:`
   and/or an Apple event handler, whichever really fires for a running `Accessory` app — check it).
2. On such a request the agent brings the UI up: if no `tandem-ui` is connected to the agent's
   IPC, it launches the sibling `Contents/MacOS/tandem-ui` (new instance, detached, from the
   agent's own bundle path); if one is connected, it asks it to show the main window (a new IPC
   message from agent to UI, or reuse an existing one; the UI calls its existing `show_main`).
3. The decision (which request, UI connected or not → launch / show / nothing) is portable
   and tested in Linux, like `app_quit.rs`; only reading the Apple event and spawning are
   behind `#[cfg(target_os = "macos")]` with a trait and a test double.
4. Log one INFO line per request ("open request from LaunchServices: launching the UI" / "showing
   the UI").
5. Document the behaviour in `docs/dev/install-macos.md` (troubleshooting) and keep DESIGN /
   DECISIONS consistent if they describe how the app is opened.

If while doing it the approach turns out impossible (for example LaunchServices never
delivers the event to an `Accessory` agent), stop, mark `blocked` with what was observed and
the alternatives; do not move the agent out of the bundle without the user deciding it.

## Notes

### What was done

- **Decision** (`crates/tandem-files/src/app_open.rs`, portable, unit + proptest): `aevt/rapp`,
  `aevt/oapp` or the reopen callback without an Apple event → `LaunchUi` with no UI connected,
  `ShowUi` with one; anything else (a Quit above all) → `Nothing`. Nothing here can terminate the
  agent: proptest checks that every event that opens the UI is one `app_quit::decide` ignores.
- **macOS delegate** (`drag_macos.rs`): `applicationShouldHandleReopen:hasVisibleWindows:`, which
  is how AppKit's own `aevt/rapp` handler reaches the delegate. It reads the current Apple event,
  calls `run_app_loop`'s new `on_open` and returns `NO`. No custom Apple event handler is
  installed, so AppKit's handling (and T-333's Quit answer) stays as is. That the callback fires
  for this `Accessory` agent is in the hardware checklist; if it does not, the next step is a
  `kAEReopenApplication` handler on `NSAppleEventManager` (same `on_open`).
- **Agent** (`crates/tandemd/src/ui_open.rs`): `UiPresence` counts the `Peer::Ui` connections of
  the IPC (clients such as `tandem mcp` do not count) and broadcasts the show request;
  `UiOpener` applies the decision and logs one INFO line per request; `SiblingUi` launches
  `Contents/MacOS/tandem-ui` beside `current_exe()`, in its own process group (launchd stopping
  the agent's job does not take the UI along), streams to null, reaped by a thread. The trait
  `UiLauncher` has a test double; `SiblingUi` itself is tested on Linux with a script.
- **Protocol v47**: `AgentToUi::ShowWindow` (only to UI connections); the UI's session calls
  `Sink::show_window` → `show_main`.

### Dock icon (field evidence of 2026-11-20)

The task now requires that `tandemd` never shows as "Tandem" in the Dock, ⌘Tab or Force Quit.
`tandemd` shares the bundle's `Info.plist`, which declares a regular app (no `LSUIElement`), so a
process from that bundle checks in with LaunchServices as a regular app unless it becomes
`Accessory` first. Until now `setActivationPolicy(Accessory)` ran in `run_app_loop`, after the
agent's thread had been spawned; that thread later connects to the window server (input engine,
displays, CoreGraphics), and a connection made before the policy is set registers the process
with the Dock as a regular app.

Chosen mechanism (no change to the bundle layout or to any signature):
`drag_macos::become_accessory()` is the first thing `tandemd`'s macOS `main` does, on the main
thread, before the agent's thread exists; `run_app_loop` sets it again (idempotent).

Looked at and not used:
- LaunchAgent plist keys: `ProcessType` only sets launchd's resource policy and
  `LimitLoadToSessionType` the session the job loads in; neither decides LaunchServices' app type,
  so neither hides a Dock icon.
- `TransformProcessType`: deprecated, and `setActivationPolicy` is its supported replacement.
- `Prohibited` policy: the drag's invisible window (T-121) needs a process that may own windows.
- Fallback if the hardware still shows the agent: `LSUIElement = true` in the shared `Info.plist`
  and `set_activation_policy(Regular)` in the UI's `setup`. The designated requirements of the app
  and of `tandemd` (identifier + certificate, T-348) do not change, but it changes how every launch
  of the UI starts, so it waits for the result of this checklist.

Note that the second field report (below) shows the dark icon of 2026-11-20 was most likely the
**UI**, not the agent; the `Accessory` ordering is kept as hardening, and the checklist item tells
whether the agent ever shows.

### Follow-up (separate root cause): the UI blocks on `launchctl`

Evidence (2026-11-20, Mac): `lsappinfo` showed the only registered "Tandem" was
`Contents/MacOS/tandem-ui` (pid 30906, state `exited-with-subordinates`, launched 09:53:27 local by
the Dock); no `tandemd` in `ps`; `/bin/launchctl kickstart -k gui/501/com.franc1sc0sv.tandem.tandemd`
stuck for 41+ s. The PC lost the Mac agent at 09:53:22 local and considered it off at 09:53:37.

Reading of the code (not changed here, it is not the LaunchServices mapping this task fixes):
1. `apps/tandem-ui/src-tauri/src/app.rs` `setup()` calls `install_agent()` →
   `launch_agent::install_from` → `ensure()` **synchronously on the main thread**, before any
   window exists. With the plist already correct and the job loaded but without a process (the
   agent had died 5 s earlier and launchd was holding it for `ThrottleInterval` 30 s), `ensure`
   runs `launchctl kickstart -k`. `SystemLaunchd::run` uses `Command::output()` with **no
   timeout**, so a hung `launchctl` freezes the UI's main thread: no window, a dimmed Dock icon
   whose Quit cannot be processed. That matches what was seen.
2. `agent_restart` ("Restart agent") is a synchronous `#[tauri::command]`, which Tauri runs on the
   main thread: same exposure. `revive_agent` already uses `spawn_blocking`, but without a timeout
   a hung call keeps a blocking thread forever.
3. Why `kickstart -k` can hang, to confirm on the Mac (`launchctl print …` for `state`,
   `last exit code`, `runs`, `spawn scheduled`/throttle; `sample <launchctl pid>`;
   `log show --predicate 'process == "launchd"' | grep tandemd`; the last
   `tandemd exiting with code N` line of `tandemd.log`): `-k` waits for the old instance to die
   (SIGTERM, then SIGKILL after the job's exit timeout; the agent's own shutdown is bounded by
   `DRAIN_TIMEOUT` 2 s plus the display restore) and then for the new spawn. With no process left,
   the likely wait is launchd's throttle on a job that just exited or is crash-looping at start
   (each new `tandemd` dying early would keep `kickstart` waiting). Why the agent died at 09:53:22
   is a separate question for that log line.

Proposed follow-up task: every `launchctl` call of the UI off the main thread (`setup` spawns
`install_agent` and reports into the first-run guide when it finishes; `agent_restart` async) and
with a timeout (kill `launchctl` after ~10 s and report "launchd did not answer"); `ensure` uses
`kickstart` without `-k` when there is no process (nothing to kill); and a test double for
`Launchd` that hangs, to check the window still opens.
