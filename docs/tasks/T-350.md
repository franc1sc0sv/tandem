# T-350 — Opening Tandem when only the agent is running

## Context

Seen on the real desk on 2026-11-20, right after a clean install of v0.3.1 on the Mac
(remove `Tandem.app`, copy the new one, the LaunchAgent starts `tandemd`):

- Only `/Applications/Tandem.app/Contents/MacOS/tandemd` was running; `tandem-ui` was not.
- macOS showed "Tandem" as open (Dock / Force Quit / app switcher), with no window.
- Opening Tandem again (Finder, Launchpad, `open -a Tandem`) brought nothing up.
- Quitting it did nothing. The unified log shows the T-333 answer:
  `applicationShouldTerminate: NSTerminateCancel` / `App termination canceled`.
- Workaround: `open -n /Applications/Tandem.app` or running `Contents/MacOS/tandem-ui` directly.

Cause: `tandemd` lives in `Tandem.app/Contents/MacOS` and runs `NSApplication.run` for the drags
(T-121, `crates/tandem-files/src/drag_macos.rs`), so LaunchServices registers it as *the*
running instance of `com.franc1sc0sv.tandem`. Opening the app then only sends the reopen/activate
Apple event to that instance (the agent, which has no window, `Accessory` policy) instead of
launching the bundle's executable (`tandem-ui`). Its Quit is ignored on purpose (T-333).

## Goal

With only the agent running, opening Tandem the usual ways (double click in Finder or
Launchpad, `open -a Tandem`, `open /Applications/Tandem.app`, Dock) shows the main window,
and Quit from the Dock/app menu of that visible app quits the UI. The agent's T-333 behaviour
(ignore Quit, stop only through launchd or at session end) stays.

## Approach (keep the architecture; do not move `tandemd` out of the bundle)

Moving `tandemd` into its own nested bundle would give it a new code identity and make macOS
ask for Accessibility, Input Monitoring and Local Network again, against T-348. So:

1. In `drag_macos.rs`'s app delegate, handle the open/reopen paths (`kAEOpenApplication`
   `aevt/oapp`, `kAEReopenApplication` `aevt/rapp`, i.e. `applicationShouldHandleReopen:hasVisibleWindows:`
   and/or an Apple event handler, whichever really fires for a running `Accessory` app — check it).
2. On such a request the agent brings the UI up: if no `tandem-ui` is connected to the agent's
   IPC, it launches the sibling `Contents/MacOS/tandem-ui` (new instance, detached, from the
   agent's own bundle path); if one is connected, it asks it to show the main window (a new IPC
   message from agent to UI, or reuse an existing one; the UI calls its existing `show_main`).
3. The decision (which request, UI connected or not → launch / show / nothing) is portable
   and tested in Linux, like `app_quit.rs`; only reading the Apple event and spawning are
   behind `#[cfg(target_os = "macos")]` with a trait and a test double.
4. Log one INFO line per request ("open request from LaunchServices: launching the UI" / "showing
   the UI").
5. Document the behaviour in `docs/dev/install-macos.md` (troubleshooting) and keep DESIGN /
   DECISIONS consistent if they describe how the app is opened.

If while doing it the approach turns out impossible (for example LaunchServices never
delivers the event to an `Accessory` agent), stop, mark `blocked` with what was observed and
the alternatives; do not move the agent out of the bundle without the user deciding it.

## Acceptance criteria

- [ ] Portable decision with unit tests (and proptest for the invariant: a Quit is never
      turned into a launch, and an open request never terminates the agent).
- [ ] The macOS delegate handles the open/reopen request and launches or shows the UI.
- [ ] New IPC message (if needed) covered by the protocol tests; protocol version bumped if
      the wire format changes.
- [ ] `cargo fmt`, `clippy -D warnings`, `cargo test --workspace` green; CI green on the
      three platforms.
- [ ] Docs updated.

      the main window appears.

- [ ] With the UI running but its window hidden, opening the app shows the window.
