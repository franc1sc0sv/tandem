# T-242 — Hardware suite scripts: concurrent cleanup, report binary, signals

## Context

Three failures of the manual hardware suite (`scripts/hw/`):

1. A previous `mac-side.sh` was stopped (`pkill`) while a new one started. The old trap ran `rm -rf /tmp/tdhw* ~/.cache/tandem-hw-*`, which deleted the NEW run's `/tmp/tdhw-<id>/bin`; the still-running Mac agent's `tunnel-process` and `tunnel-port` checks then failed with `could not launch: /tmp/tdhw-005106/bin/tandem-hw: No such file`.
2. A manual-mode `run.sh` ended with `done (code 127)` and no report. The report is written by the Linux `tandem-hw`, which was stale (built from an old revision) or missing: with `--skip-build` nothing rebuilt it, and nothing checked it before running it.
3. When `run.sh` was killed, the cleanup deleted the PC folder and the agent log with the evidence of a dropped link.

## Fix

- `mac-side.sh`: the trap removes only this run's `--mac-dir`, and `--mac-dir` is refused if it is `/`, `$HOME` or a parent of it, has `..`, or (in real mode) is not under `/tmp`. The source and build cache are per commit (`~/.cache/tandem-hw-{src,target}-<commit12>`), so two runs at different commits never `git checkout -f` the same tree. Each run registers `~/.cache/tandem-hw-locks/<commit12>.<pid>` BEFORE using the cache (the run.sh one-liner does it before cloning, and `exec`s the script with the same pid) under a `mkdir` mutex that the cleanup also holds while it checks and deletes, which closes the race between a finishing run and a starting one; stale locks (dead pids) are ignored and the last run out of a commit deletes that commit's cache. The header documents `--hold`.
- `run.sh` (ssh mode): the Mac cache removal at the end respects the same lock files and leaves the cache alone while any run is alive.
- `run.sh`: the Linux `tandem-hw` for the report is always built from the same ref (also with `--skip-build`), copied to the run folder, and missing or failed builds stop the run with a clear message before any step.
- `run.sh` signals: INT, TERM and HUP now run the cleanup (exit 130, 143, 129). Step output used to be redirected on the call of the background function, so the cleanup lines of a signal arriving mid-step went to the step's error file; the redirection now lives inside the background job and the cleanup prints to the saved original stderr.
- `run.sh` cleanup copies the PC agent logs (`agent.out`, `agent.err`, `data/logs`) and the Mac ones to `<run>/out/final-logs/` before deleting the folders, also when killed.
- `scripts/hw/test-cleanup.sh` (by hand, never in CI) covers the concurrent Mac cleanup with stubbed `git` and `cargo`, and the SIGTERM of `run.sh --sim` mid-step. It fails with the old `mac-side.sh`.

## Criteria

- [x] Killing one `mac-side.sh` leaves another run's folder and cache intact (same commit: shared cache, last one out removes it; different commits: separate caches).
- [x] A `--mac-dir` of `/`, `$HOME` or outside `/tmp` is refused and deletes nothing.
- [x] The report binary is always rebuilt from the ref and a missing one fails clearly.
- [x] `run.sh` prints `cleanup`, leaves no agent behind and exits 143 on SIGTERM in the middle of a step.
- [x] The PC agent logs are saved in `out/final-logs/` before the PC folder is deleted, also on SIGTERM.
- [x] `run.sh --sim`, `test-manual-sim.sh` and `test-cleanup.sh` pass; `bash -n` on all scripts.
- [x] `scripts/ci/english.sh`, `tasks.sh`, `timeouts.sh` and `safety.sh` pass.
