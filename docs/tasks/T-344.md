# T-344 — Local Network permission is never requested

Found on real hardware on 2026-11-19 (Mac managed by an MDM).

## What happens

- Setup step 3 shows "Local Network · Not checked · macOS asks the first time". macOS never asked, and Tandem did not appear in System Settings → Privacy & Security → Local Network.
- Without it, the two machines did not find each other for pairing (the PC was waiting on its pairing port and announcing over mDNS). Pairing only worked after the user ran `tandemd` by hand from a terminal, which uses the terminal's Local Network permission.
- macOS may not show the prompt for a process started by launchd; the "responsible process" of `tandemd` is decided by how it is launched.

## Scope

1. Find, on the Mac, what makes macOS show the Local Network prompt for `tandemd` started by the LaunchAgent, and attribute it to Tandem (for example `AssociatedBundleIdentifiers` in the plist, launching the agent so the app is its responsible process, or a first multicast send from the app process). Record what was tried and what worked in Notes.
2. Step 3 detects the real state (the agent can tell "denied" from "not asked" by the error of a multicast or local unicast send) and offers a button that triggers the prompt again, like Accessibility.
3. If the permission is denied or blocked by a profile, step 3 and the Network screen say so with the path to the setting, instead of waiting forever for the other machine.

## Notes

### Research (sources in `docs/research/macos-local-network.md`)

- Apple TN3179: launchd **daemons**, root and anything started from Terminal or SSH are exempt from local network privacy; launchd **agents** are not. That is why `tandemd` worked from a terminal and not from the LaunchAgent.
- TN3179: "If you ship a `launchd` agent that's not installed using `SMAppService`, make macOS aware of the responsible code by setting the `AssociatedBundleIdentifiers` property in your `launchd` property list." Tandem's agent is installed with `launchctl bootstrap` and its plist had no such key. `NSLocalNetworkUsageDescription` and `NSBonjourServices` belong in the app's `Info.plist`, where they already are.
- TN3179: the alert is not shown for a process that exits right after the blocked operation. `tandemd` is long-lived, and the probe runs inside it.
- TN3179: there is no API for the state (FB8711182), and MDM cannot configure local network privacy, so the managed Mac is not the cause by itself.
- Forums (Quinn, Apple DTS, threads 765285 and 778457): a BSD send to a local address fails with `EHOSTUNREACH` both while the alert is pending and when denied; no errno tells them apart. Thread 774160: `AssociatedBundleIdentifiers` may still leave the alert naming the agent (FB16563823), but the alert appears.

### What was implemented

- `tandem_ui::launch_agent::plist`: `AssociatedBundleIdentifiers = [com.franc1sc0sv.tandem]` (`APP_BUNDLE_ID`, tested against `tauri.conf.json`). Agents installed before are rewritten and reloaded when the app opens.
- `tandemd::local_network`: `Probe` trait (real `UdpProbe`: a zero-length datagram to `224.0.0.251:9`, no ARP), the pure `Tracker` (granted when a send goes through; denied after 20 s of `EHOSTUNREACH` or right after a success; unknown otherwise; a one-off error keeps the state) with a proptest invariant, and the task that probes every 5 s while not granted (60 s when granted) and at once on `UiCommand::CheckLocalNetwork`. Started only on macOS with the real backends.
- Protocol v44 (v43 is T-345 in #203): `Capabilities::local_network: Option<LocalNetwork>` and `UiCommand::CheckLocalNetwork`. The app passes it to the frontend as `local_network: "granted" | "denied" | "unknown" | null` and maps the `check_local_network` action.
- UI: step 3 shows the probed state with "Ask again" and "Open settings"; the pairing step (while looking for the other machine) and the Network screen show "Local Network permission missing on this Mac" with the System Settings path when it is denied. An unknown state is never blamed.
- Not done, kept as fallbacks for the real Mac (see the research note): a probe from the app process, an embedded `Info.plist` in `tandemd` (it would change the code-signing identifier TCC uses for Accessibility and Input Monitoring), and installing with `SMAppService`.
- Overlap with #197/#198 (T-331/T-332): they change `KeepAlive` in the same plist; this one adds a key after `ProgramArguments`, so a rebase only touches the expected-plist test.
