# T-090 — macOS permissions that are really requested and verified

## Context

User report (MacBook M5, macOS in English, Tandem installed from the CI `.dmg` with ad-hoc signing, `tandemd` launched by the LaunchAgent): the "missing permissions" notice and step 1 of the wizard kept saying that Accessibility / Input Monitoring were missing even though the user had granted them in Settings (added `tandemd` with "+", removed it and added it again, restarted the agent with `launchctl kickstart -k`).

## What was read in the code (checked)

- `tandemd` decides what is missing with `AXIsProcessTrusted()` and `CGPreflightListenEventAccess()` on **its own process** (`tandem_input::macos::capture::permissions`).
- `request_permissions()` (`AXIsProcessTrustedWithOptions` with prompt and `CGRequestListenEventAccess`) existed but **nobody called it**: macOS never received the request made by the running binary, so it did not show its dialog or register it by itself; everything depended on adding it by hand with "+".
- The UI could not say **which binary** the permission had to be granted to: the guide had the fixed path `/Applications/Tandem.app/Contents/MacOS/tandemd`, without knowing which one was really running, and the user had no way to see the pid or whether the agent had restarted.
- The LaunchAgent (`launch_agent.rs`) points to the `tandemd` of the app that runs, with `KeepAlive.SuccessfulExit=false`: it is only brought back up if it dies with an error, which is why restarting is done with `launchctl kickstart -k`, which did not need a terminal if the app did it.

## What is assumed (not checked, requires the Mac)

The exact cause on the user's Mac cannot be confirmed without hardware. The hypotheses, which this task attacks all with visible diagnostics instead of guessing:

1. TCC entry tied to another binary or signature: with ad-hoc signing the entry is valid for the exact *cdhash*; an entry from an earlier version shows as enabled in Settings and is not valid for the current binary. Requesting the permission from the running binary replaces it.
2. `CGPreflightListenEventAccess` and similar are evaluated once per process: what was granted is valid after restarting the agent.
3. A `tandemd` different from the one that runs (another path): now the real path and the pid are visible in the UI.

## Scope

1. `tandemd` requests the missing permissions **once at startup** (`InputBackends::request_permissions`) and afterwards only on explicit order from the UI; never in a loop (each request is a system dialog).
2. Protocol v14: `UiCommand::RequestPermissions` ("Request permissions" button) and `InputCaps.process` (`ProcessInfo`: executable path, pid and start time) in the capabilities.
3. UI: step 1 of the wizard and the permissions guide show "Grant the permission to this binary: <path> (pid N)", the state of each permission according to the agent, "Request permissions", "Open settings" and "Restart agent" (`launchctl kickstart -k` from the app, `launch_agent::restart`, without asking the user for commands). If it was already enabled and is still missing, it explains how to remove the old entry.
4. The permission names appear both as Tandem calls them and as macOS labels them (System Settings → Privacy & Security → Accessibility / Input Monitoring / Local Network).
5. `docs/dev/install-macos.md` with the real flow.

## Acceptance criteria

- [x] With missing permissions, the agent requests them once at startup and does not repeat them while they remain missing (integration test with a simulated backend).
- [x] `RequestPermissions` requests them again and the new state reaches the UI (test).
- [x] With no permissions to request, no dialog is opened (test).
- [x] The capabilities carry the process's path, pid and start time (`tandemd` and protocol tests, walk over all the variants).
- [x] `launch_agent::restart` only restarts a loaded agent (test with a simulated `launchctl`); the plist keeps `KeepAlive`.
- [x] Step 1 and the guide show the path, both names (Tandem's and macOS's) and the "Request permissions" / "Restart agent" buttons (frontend tests of the views and of the button handlers).
- [x] `docs/dev/install-macos.md` updated.
- [x] Quality gate (`fmt`, `clippy -D warnings`, `test`) and frontend tests.

## Notes

- Protocol v14 requires updating Mac and PC at the same time: a v13 agent rejects the link with `IncompatibleVersion`.
- Without a Developer ID each new version of the app changes the cdhash and macOS asks for the permissions again (see `docs/dev/install-macos.md`).
- The restart is done by the app with `launchctl kickstart -k`, not by the agent exiting: with `SuccessfulExit=false` a clean exit of the agent would not bring it up again.
