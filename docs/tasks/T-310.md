# T-310 — Path failover above 1 s

Found by the acceptance agent (part B, round 6, `docs/reports/acceptance-2026-11-19-b6.md`), flow F6 ("cut the main path → input moves to the next in < 1 s"), screen P7 (`V3-Network`).
`harness/` below is `docs/reports/acceptance/2026-11-19-b6/harness/`.

## What fails

Two real agents over loopback (`acc_host`, `--sim-backends` doubles), paired through the UI, with three paths through UDP proxies (`harness/px.mjs`, `harness/netcfg.mjs`: USB4, Ethernet and Wi-Fi, each on its own loopback address). A cut of the USB4 proxy is a dropped cable: every packet is lost from that instant. The time is from the cut to the first snapshot of the agent (`agent_snapshot`, polled every 20-40 ms) whose `peer.link` is another path.

- `harness/f6fail.mjs nw12 25`: 25 cuts on one pair, each at a random phase against the health ping. **5 of 25 took 1 s or more**: 1127, 1115, 1001, 1270 and 1124 ms. The others: 286-931 ms.
- `harness/f6b.mjs` (the official F6 check) on 18 fresh pairs (13 macOS+Windows, 3 Windows+Windows, 2 macOS+macOS): 15 under 1 s (309-955 ms), and 3 over: 1207 ms (`nw3`), 1241 ms (`nw10`) and 1271 ms (`mm6`, on `develop` at `fe92474`).
- The agent's own measure agrees. Network shows "Spike when the cable was unplugged · switched to Ethernet in 1.2 s" or "in 1.3 s" after **every** cut of the round (`fin`, `ww`, `mm` and the other pairs). That number is `PathSwitch::took_ms`: the time from the dropped path's last answer until the next path took the traffic, the most input went without a path.

## Cause

The design allows it. `HealthConfig` (`crates/tandem-link/src/manager/mod.rs`) pings each link every 1 s and waits 250 ms for the Pong. A cable that drops right after a good ping is only noticed at the next ping's timeout, up to 1.25 s later. The doc comment says detection "has to stay under 1.5 s", and the manager test `preferred_dropping_switches_in_under_1_5_s_and_comes_back` checks `MAX_SWITCH = 1500 ms`. But `docs/DESIGN.md` §6 ("on a failure, input moves to the next path in < 1 s") and `docs/ACCEPTANCE.md` F6 ask for under 1 s. Earlier rounds passed because only one or two cuts were timed per round.

## Expected fix

- Detect a dropped active path within the 1 s budget, with margin for the switch itself. For example, ping the active link more often than the backups (such as every 250-300 ms, Pong timeout 250 ms), or treat the input stream's own silence as a failed ping. Keep the backups at 1 s if that matters for Wi-Fi power.
- Change `MAX_SWITCH` in the manager tests to under 1 s and add a test where the cut lands right after a good ping (the worst case). It must fail before the fix.
- Update DESIGN §6 and the `HealthConfig` comment so the numbers agree. `scripts/ci/protocol.sh` checks the constants listed in DESIGN.
