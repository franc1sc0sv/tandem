# T-008 — Orchestrator: plans executed across the two machines

## Scope

In tandemd: when a mode is requested, generate the `Plan` (tandem-core) and run it with an `Executor` that dispatches each step to the machine that must execute it (local, or to the peer over the control plane), with a per-step timeout (configurable; 120 s for powering on the PC, 10 s for the rest).
Transaction progress published over IPC to the UI. Steps without a real implementation yet answer with a clear error (`not implemented`), which triggers the rollback.

## Acceptance criteria

- [x] Test with two in-process agents (loopback) and simulated executors: a mode applied end to end; a remote failure causes the rollback and the final state is the initial one.
- [x] A step timeout → rollback (test with a paused tokio clock).

## Notes

- `tandemd::orchestrator`: `target(step)` decides where each step runs: `PowerOnPc` and `SetBuiltin` on the Mac (Wake-on-LAN goes out from the Mac), `PowerOffPc` and `SwitchInput` on the PC (DDC over DisplayPort, DESIGN §8), `Attach`/`Detach` on the step's machine and `UpdateInputGeometry` on both (the orchestrating one first). `Dispatcher` implements `tandem_core::Executor`: it wraps each step with its timeout and publishes `TxnEvent` (Started, StepStarted/Done/Failed, RollingBack and the outcome Committed/RolledBack/Inconsistent). The rollback is still `tandem_core::run`'s.
- Timeouts in `tandem.toml`, section `[orchestrator]`: `power_on_timeout_secs` (120 by default) and `step_timeout_secs` (10); 0 is invalid. The agent that serves a step from the other also applies the same cap, so as not to block its stream with a hung step.
- Local steps behind the `LocalSteps` trait; `Unimplemented` (what `tandemd` uses today) answers `«<step>: not implemented»`, so a mode change requested by the UI rolls back with that reason. Without a connection to the other agent (`NoPeer`), remote steps fail with «the other agent is not connected».
- `tandemd::peer`: each agent opens its own control stream to the other (`PeerClient`, tandem-proto's `ExecuteStep`/`StepResult` messages) and serves all the streams the other opens (`accept_streams`/`serve`), which also answer `Ping`/`GetState` and accept `State`. This way either one can orchestrate and the link manager's ping stream is also served. The requested steps run one at a time and in order, and those that do not belong to that machine are rejected. When finished, the orchestrator sends the final state to the other agent.
- IPC: `SetMode` and `MoveMonitor` answer `Accepted { txn }` and progress arrives as `AgentToUi::Txn`; a second change while another is in progress is rejected («a change is already in progress»). `SetBuiltin` is still rejected as «not implemented yet»: the built-in display preference is not a mode change and arrives with its own task.
- Tests: real QUIC over loopback with two agents and simulated steps (`tests/orchestrator.rs`: mode applied end to end with the PC off, failure on the PC with return to the initial state on both agents, the PC as orchestrator); timeouts with a paused tokio clock, local and remote (the remote one with the real protocol over an in-memory stream).
- Out of scope: `main` does not yet open connections with the other agent (identity and trust loading are missing, and so is connecting T-005's link manager with `PeerClient`/`accept_streams`); two simultaneous transactions started on different machines are not coordinated with each other.
