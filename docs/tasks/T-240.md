# T-240 — Key probe notices lost when a machine's own link is not installed yet

## Context

`the_reduced_wizard_end_to_end` (`crates/tandemd/tests/wizard.rs`) failed on `ubuntu-latest` in the CI run of PR #167 (T-239, an unrelated change; the re-run passed):

```
the test exceeded the maximum time waiting at crates/tandemd/tests/wizard.rs:219:17
```

Line 219 is the wait for the Mac to hear the PC's key (`probe.wait_for(|s| s.heard.is_some())`). The wait for the PC to be armed (line 211) had already passed.

## Acceptance criteria

- [x] The cause is identified and described in `## Notes`.
- [x] A test forces the order that loses the notice and fails before the fix.
- [x] The daemon repeats the key probe notices when a link appears.
- [x] The test passes in a loop under CPU load.
- [x] Quality gate and CI green.

## Notes

**Cause:** each agent has a link of its own toward the other. `Agent::set_peer` installs it when that agent's link manager has an active link, and until then `orch.peer()` is `NoPeer`, whose `send` drops the message. The tests (and the wizard) only wait for the first agent's link (`PingPeer` on A). The other agent receives A's `Arm` over A's connection, so it is armed even though its own link is not installed. When the key is then heard on it, `heard_key` tells A through `NoPeer.send`: the `Heard` is lost and nothing repeats it. `PeerLink::send` documents that a notice lost without a link "is repeated when the next link appears", and `set_peer` repeats the desk, the capabilities, the monitors and the version, but not the key probe. It is a race between two managers, so it only shows when the runner is slow enough for B's link to lag behind A's. The same hole exists for an `Arm` sent while A has no link.

**Fix:** `set_peer` now calls `Agent::replay_key_probe`: if the test is armed it sends `KeyProbeMsg::Armed` and, if this machine heard a key, `KeyProbeMsg::Heard`. `Armed` is a new message that only turns listening on, so it does not clear what the receiver heard (`Arm` does). `Heard` was already idempotent (`hear` ignores a machine already recorded). `Armed` goes last in `KeyProbeMsg` so the existing discriminants keep their values, and `PROTOCOL_VERSION` bumps to 41 because the enum gained a variant.

**Forcing test:** `wizard.rs::a_key_heard_before_its_own_link_is_up_still_reaches_the_other` starts B with `dial: false` (B's link only appears when its manager retries and adopts A's connection, seconds after A's), asserts B has no link, hears the key on B and waits for A to know. It timed out at the same wait (`wizard.rs:432`) before the fix and passes after it. Unit tests in `agent/setup.rs` cover the replay, its absence when nothing runs and the idempotence of `Armed`/`Heard`.

**Evidence:** I could not make the original test fail locally in 150+ runs under load (8 concurrent copies pinned to one core with 24 `yes` processes), because the race needs B's link to lag; with B's link forced to lag the failure is immediate. After the fix, 48/48 runs of the whole `wizard` binary (5 tests) under that load pass.
