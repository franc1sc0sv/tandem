# T-250 — "Save and apply" lands on Monitors instead of the progress

Found by the acceptance agent (part B, round 4, `docs/reports/acceptance-2026-11-19-b4.md`), flow F3 ("apply successfully"), screen P9 (`F-Transactions`).

## What fails

Two real agents, the scene editor on machine A (`#/monitors/scene`), a new scene that moves a monitor, **Save and apply** (`docs/reports/acceptance/2026-11-19-b4/harness/f3prog.mjs`, run 8 times on a fresh pair and 6 times on another):

- In 5 of 8 runs (4 of 6 on the other pair) the window goes from the editor straight to Monitors. "Changes in progress" is never rendered, not even for one frame. The scene is applied (the monitor double switches input, both agents record the transaction), so only the progress is lost.
- In the other runs the window shows "Changes in progress" with the steps, as `F-Transactions` draws it.

Trace of a failing run (window clock, ms):

```
2145 call  agent_act apply_scene
2147 reply agent_act apply_scene        -> the editor calls store.showProgress()
2160 hash  #/monitors                   -> Progress.svelte redirected
2176 event agent-notice txn started     -> the transaction's first notice, too late
2176 event agent-notice txn committed
```

In the passing runs the `started` notice arrives before the progress screen mounts.

The "Apply" button of a scene card goes through the same `store.applyScene` + `store.showProgress()` path and passed the 4 times it was tried here, so it is exposed to the same race with a different timing.

## Cause

`apps/tandem-ui/src/screens/Progress.svelte`:

```ts
$effect(() => {
  if (store.txnReady && store.run === null && store.powerRun === null && !meter) store.go({ screen: "monitors" });
});
```

The agent answers `ApplyScene` before it sends the transaction's `started` notice, and the reply and the notices travel on different channels (Tauri command reply vs. event). When the reply wins, the screen mounts with `store.run === null` and leaves at once. In a window that already ran a transaction, `store.run` still holds the old one, so the bug only shows on the first change of a window, or whenever the race is lost.

## Expected fix

- The progress screen must not leave while a change the window asked for is still expected (for example: `applyScene`/`switchMonitor`/`setPower` set a pending origin, and Progress waits for the `started` notice or a short timeout before giving up). An empty transaction (nothing to change) can still go back to Monitors with a notice.
- A store test that delivers the command reply before the `started` notice and checks that the window stays on Progress and then shows the steps; it fails before the fix.
