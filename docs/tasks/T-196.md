# T-196 — The cable link is not recognized as USB4

## Context

Hardware run over the Thunderbolt 4 cable (`docs/reports/hw-2026-11-18-cable.md`):

- The peer address configured by the user (`peer = "169.254.x.y:47871"`, the cable's link-local IPv4) becomes `LinkCandidate { kind: Wifi }`, so the link is reported as Wi-Fi and the Wi-Fi data cap (10 MB/s) throttles tunnels and files.
- On Windows, `tandem_link::iface::follow` detects the "USB4(TM) P2P Network Adapter" as `Ethernet`.
- The IPv6 link-local candidate learned through mDNS (`[fe80::…%13]:47871`) fails every attempt with `Connect(InvalidRemoteAddress)`. The scope id looks like the peer's interface index, not the local interface that faces the cable.

## Expected fix

- Classify a candidate by the local interface that routes to it (Thunderbolt Bridge on macOS, USB4 P2P adapter on Windows → `Usb4`), not by how it was learned.
- When dialling an IPv6 link-local address, use the local interface's scope id.
- Tests with simulated interface tables for both platforms; a test that a link-local peer on a USB4 interface gets the USB4 QoS profile.

## Acceptance criteria

- [x] A configured link-local peer on the cable interface is classified `Usb4` on macOS and Windows (unit tests with simulated interface tables).
- [x] IPv6 link-local candidates are dialled with the local scope id (test).
- [x] The USB4 QoS profile applies to that link (test).
- [x] Quality gate and CI green.

## Pending hardware verification

- [ ] Repeat the cable run: link reported as USB4, files throughput well above the Wi-Fi cap.
- [ ] On Windows, `GetAdaptersAddresses` returns "USB4(TM) P2P Network Adapter" as the description of the cable adapter.
- [ ] The IPv6 link-local candidate over the cable connects (dual-stack endpoint on Windows and macOS).

## Notes

- The configured peer stayed `Wifi` because `kind_for_addr` matched IPv4 by `/24`, and the two cable ends (`169.254.252.182`, `169.254.93.252`) are in different `/24`s. IPv4 link-local now matches any interface with a `169.254/16` address, preferring the best kind; `::ffff:` peers from a dual-stack socket are unmapped first.
- On Windows the adapter's friendly name is "Ethernet N"; the kind now comes from the hardware description (`GetAdaptersAddresses`), falling back to the name (`classify_adapter`, `interfaces_from_rows`).
- `InvalidRemoteAddress` came from quinn: the endpoint was bound to `0.0.0.0` (all static peers IPv4) and an IPv4 endpoint cannot dial IPv6. The scope id was already the local one (mDNS tags answers with the receiving interface and `plan` rescopes with the local index); a test pins that. The endpoint now binds `[::]` dual-stack (`IPV6_V6ONLY` off, needed on Windows) and falls back to `0.0.0.0` on a host without IPv6.
