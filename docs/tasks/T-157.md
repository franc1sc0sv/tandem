# T-157 — The cursor lock works but the UI does not say so

Found by the acceptance agent (part B), flow F12.

## What fails

The palette's "Lock here" command does lock (with two real agents: `input.locked` becomes `true`, the server's cursor does not cross the edge; "Remove the lock" releases it and it crosses again). But the window never shows the state: `InputView.locked` is not read on any screen, there is no notice on locking or releasing, and the palette always offers "Lock here" and "Remove the lock" at the same time. The user cannot know whether the lock is on (and the cursor "does not cross" with no explanation). If the machine is not the one that has the keyboard, the rejection is explained ("this machine is not the one that has the keyboard").

## Screenshots

- App: `docs/reports/acceptance/2026-11-18-b/F12-ajustes-paleta/04-bloqueado-ui.png`.
- Mockup: `mockups/v03/F-Paleta.dc.html`, `V3-Puesto.dc.html`.

## Expected fix

- A visible "Cursor locked here" mark on the Desk (and in the tray) while `locked`, with the shape of the status chip of the button/chip system.
- Notice on locking and on releasing; the palette shows only the option that applies (`detail` with the state).
- Vitest test with the bridge and a test with two agents.

## Acceptance criteria

- [x] The locked state is seen in the UI and removed on releasing.
- [x] The palette offers only one of the two commands according to the state.
- [x] Quality gate and CI green.
