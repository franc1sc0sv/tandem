# T-342 — Scenes apply in about 7 s

Found on real hardware on 2026-11-19. The 34" changes input almost at once, but the app keeps the old state for several seconds. Mac agent log:

```
05:31:49.62 transaction txn=1 what="apply scene \"Work\"" steps=2
05:31:56.62 transaction applied txn=1
05:31:57.97 transaction txn=2 what="apply scene \"Only Mac\"" steps=2
05:32:04.82 transaction applied txn=2
```

Seven seconds per scene, both directions, with the owner (the PC) switching over DP.

## Scope

1. Find where the time goes, with timestamps per step: the `SwitchMonitor` step on the owner (Set `0x60`, waiting for the firmware's `switch-done` verdict through the event ring, `crates/tandem-monitor/src/local.rs`), the report back to the other machine, the geometry step, and the UI notice. Suspects, not confirmed: `monitors.rs` `poll_every: 1 s` / `scan_every: 5 s`, or a step waiting for a fresh monitor report instead of the verdict.
2. Fix it so a scene is reported applied right after the firmware's verdict. Target: under 1 s from the click to the UI showing the new state when the firmware confirms within that time.
3. A test with `FakeMonitor` (verdict after 300 ms) that fails before the fix: the transaction is applied in under 1 s.

## Acceptance criteria

- [x] The cause is written in Notes with the timestamps that prove it.
- [x] Test: scene with a verdict after 300 ms is applied in under 1 s (two agents, `tandem-sim`), failing before the fix.
- [x] The UI shows the new active scene and the monitor's input as soon as the transaction is applied.
- [x] Quality gate and CI green.

## Pending hardware verification

- [ ] On the real desk, `Work` ↔ `Only Mac` is shown applied in under 1 s after the click, in both directions and from both machines.

## Notes

### Cause, with timestamps

Owner side (PC, `%APPDATA%\Tandem\logs\tandemd.log`, UTC) next to the Mac log above:

| Mac | PC (owner) | |
|---|---|---|
| 05:31:49.62 `transaction txn=1` | | click on "Work" |
| | 05:31:50.341 `input switch input=DP` | the `Set 0x60` starts 0.72 s after the click |
| 05:31:56.62 `transaction applied txn=1` | | 6.28 s after the `Set` |
| 05:31:57.97 `transaction txn=2` | | click on "Only Mac" |
| | 05:31:58.643 `input switch input=HDMI` | 0.67 s after the click |
| 05:32:04.82 `transaction applied txn=2` | | 6.18 s after the `Set` |

How long the firmware takes to give its verdict, measured on the next switch of the same session. The agent keeps only the last 20 events per monitor, and the 05:31 ones were already gone. The 34"'s event ring was read from the running agent over IPC (`GetMonitors`, read only). `input switch input=DP` at 05:37:09.820 → `switch-done DP` at 05:37:11.980, so **2.16 s** from the request to the firmware's verdict.

So of the ~6.2 s from the `Set` to "applied", about 2.2 s is the firmware's verdict. The other **~4 s comes after the verdict**. A scene is `ShowMachine` + `Geometry` (`steps=2`). `ShowMachine` is the owner's `SwitchMonitor`, which returns with the verdict. `Geometry` (`RealMonitors::geometry`) then waited until the monitor views showed the new input, and nothing put it there except the owner's next full reading of the bus (`MonitorHub::tick`). That reading re-reads the whole event ring (3 DDC requests per event, the same events `switch_input` had just read), plus the live state, and a scan every 5 s. All of that is serialized on the bus, at tens of ms per request over dxva2, before `ControlMsg::Monitors` reaches the Mac.

The 0.7 s between the click and the `Set` is the same bus: the switch waits for the reading in progress to end.

### Fix

The verdict is a reading of the owner, so its input is shown at once:

- `MonitorControl::confirmed` (in `MonitorHub`) writes the confirmed input into the owner's report in the directory.
- The orchestrator calls it after every `SwitchMonitor` with a verdict: on the owner (`run_local`, also when the other machine asked for the step) and on the machine that asked (`attempt`, when the reply arrives).
- The owner also sends its list with the new input to the other machine right away, before the step's reply. The other machine's views and UI do not wait for the next reading either.
- `Geometry` and the UI (`AgentToUi::Monitors`, then the state with the scene when committed) no longer depend on the next reading.

### Test

`a_scene_is_applied_right_after_the_verdict` (`crates/tandem-sim/tests/scene_monitors.rs`). Until now the sim's DDC took time only on the monitors' clock, so every scene applied in 0 s on tokio's clock and no test could see this. `DeskBuilder::ddc_takes_time` (`MonitorHub::charge_bus_time`) makes each DDC request take its time on the desk clock too, one at a time per machine: 40 ms per request for the PC, 60 ms for the Mac, and the verdict 300 ms after the `Set`.

"Work" ↔ "Only A", from both machines. Before the fix the first scene took **1.65 s** and the test failed; with it, every scene is applied in under 1 s. At that moment the machine that asked shows the scene and the new input, and so does the other machine.

### What is left

- **The firmware's own verdict takes ~2.2 s on the real 34"** (above), plus the time `monitor-ddc` takes to read it from the ring. That is a floor for the hardware check below. Under 1 s needs a faster verdict from the firmware (`monitor-firmware`); nothing in Tandem can remove it.
- A click that lands while the owner is reading the bus still waits for that reading (the 0.7 s above). In the test, the clicks come once the bus is quiet. Making that reading cheaper, or letting a switch go first, is in `tandem-monitor/src/local.rs` and is not done here.
