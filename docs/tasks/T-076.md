# T-076 — Release en CI

## Alcance

Workflow de GitHub Actions que, al empujar un tag `v*` o a mano, construye los instaladores de macOS y Windows, genera checksums y crea un release en borrador con los artefactos y notas generadas a partir de las tareas integradas.

## Criterios de aceptación

- [x] Ejecución manual (workflow_dispatch) en modo prueba produce los dos instaladores y checksums como artefactos, sin publicar un release.
- [x] docs/dev/release.md.

## Notas

- Workflow `.github/workflows/release.yml`: tag `v*` → release en borrador; a mano (`workflow_dispatch`) con la entrada `prueba` (por omisión `true`) → solo artefactos; PR que toque el workflow o `scripts/release/` → modo prueba. Jobs: `preparar` (versión, modo, notas), `dmg (macos-latest)`, `instalador (windows)` (con la prueba de instalar/desinstalar), `checksums` (`SHA256SUMS.txt` y artefacto `tandem-<versión>`) y `release (borrador)`, el único con `contents: write` y que no corre en modo prueba.
- `scripts/release/version.sh`: la versión tiene que coincidir en `Cargo.toml`, `tauri.conf.json` y `package.json`, y el tag ser `v<versión>`.
- `scripts/release/notes.sh`: notas desde el tag anterior a partir de los squash `T-<id>: ... (#pr)`, agrupadas por la fase de cada tarea, con «Otros cambios» y la lista de tareas con verificación en hardware pendiente.
- `scripts/release/test.sh`: pruebas de los dos scripts sobre repos desechables; las corre `preparar` y el job de Ubuntu del CI.
- `workflow_dispatch` solo se puede lanzar cuando el workflow esté en `main` (rama por omisión), que solo toca el usuario. El modo prueba se comprobó con el disparo por PR, que sigue el mismo camino (mismos jobs, sin `release`).
- La firma real (Developer ID / Authenticode) en el release queda para cuando el usuario cargue los secretos; ver `docs/dev/release.md`.
