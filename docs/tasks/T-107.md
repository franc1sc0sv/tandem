# T-107 — Workspace de git

## Contexto

DECISIONS D8; DESIGN §8.

## Alcance

1. `tunnel_open { …, workspace: { repo_path } }`: en el origen, `git bundle` de la rama actual + parche de cambios sin commit (incluye archivos nuevos no ignorados); en el destino, carpeta de trabajo `<datos>/workspaces/<túnel>` con el clon del bundle y el parche aplicado. `cwd` por omisión de los procesos del túnel.
2. `bring_back { tunnel }`: en el destino, commit de lo pendiente si se pide; bundle de los commits nuevos; en el origen, rama `tandem/<túnel-o-título>` creada sin tocar la rama actual ni el árbol de trabajo. Devuelve la rama y los commits.
3. Limpieza del workspace al cerrar el túnel (configurable: conservar).
4. Funciona con repos que usan worktrees y con submódulos (estos se copian como están).

## Criterios de aceptación

- [x] Pruebas con repos temporales reales (git en PATH en CI): ida con cambios sin commit, commits en el destino, vuelta como rama; el origen no cambia su rama ni su árbol.
- [x] Puerta de calidad y CI en verde en las tres plataformas.

## Notas

Hecho:

- Protocolo v33: `TunnelUp::Workspace(WorkspaceUp::{Prepare, Checkout, Pack})` y `TunnelDown::Workspace(WorkspaceDown)`, `UiCommand::OpenTunnel { workspace: Option<WorkspaceSpec { repo_path, keep }> }`, `UiCommand::BringBack { tunnel, commit, name }` y `Reply::BroughtBack(BringBackReport { branch, commits, committed_pending })`.
- Crate `tandem-workspace` (portable). Lo único del sistema es `Git` (`SystemGit` invoca `git` con `core.autocrlf=false` y sin heredar `GIT_DIR`/`GIT_INDEX_FILE`; `FakeGit` para pruebas de orquestación).
  - Ida: `git bundle` del `HEAD` y parche (`diff --cached --binary` contra un índice temporal tras `add -A`: incluye lo nuevo sin seguimiento, respeta `.gitignore` y no toca el índice del usuario). Viajan como archivos (`tandem-files`, reanudables) a `<datos>/workspaces/<túnel>.in`; la destino hace `init` + `fetch` del bundle + `apply`, y el `cwd` por omisión de los procesos del túnel (`HostTunnel::set_default_cwd`, no vale en `wsl:`/`docker:`) pasa a ser la carpeta `<datos>/workspaces/<túnel>`. Los commits de la destino salen a nombre del usuario del origen (se manda su `user.name`/`user.email`).
  - Vuelta: con `commit`, la destino hace commit de lo pendiente; lo pendiente sin pedir commit no vuelve. Bundle de `base..HEAD`, `fetch` en el origen a `tandem/<nombre>` (nombre por omisión: el título del túnel; si existe, `-2`, `-3`…). El `fetch` no toca la rama actual, el índice ni el árbol de trabajo. Sin commits nuevos: `branch: None`.
  - Limpieza al cerrar el túnel (`Resource`), salvo `keep: true`. Un `open` que falla cierra el túnel.
  - Worktrees: se prueban con un worktree enlazado real. Submódulos: se copian sus archivos tal cual (sin su `.git`) y el parche los ignora; en la vuelta siguen siendo la entrada `160000`.
- `tandem-files`: `Files::serve_request` y `MemPath::with_server` (para colgar otros módulos). `tandemd`: `Agent::workspaces()`, los pedidos solo desde un cliente (la UI recibe `Rejected`, D9) y `OpenTunnel` con workspace y `BringBack` corren en su propia tarea (tardan).
- Pruebas: repos de git reales en carpetas temporales (`crates/tandem-workspace/tests/roundtrip.rs`: ida con cambios sin commit, binarios y archivos nuevos, commits en la destino, vuelta como rama con el origen intacto, worktree, submódulo, limpieza y `keep`, errores) y `crates/tandemd/tests/workspace.rs` con dos agentes reales por QUIC en loopback (como `files.rs`, no con `start_pair!`, que arma el emparejamiento completo).

Para otras tareas: T-108 expone `tunnel_open { workspace }` y `bring_back { tunnel, commit, name }` sobre estos `UiCommand`.

Límites conocidos: si el repo de origen avanzó o rehízo su historia y ya no tiene el commit base, `bring_back` falla con el error de git (el bundle lo necesita); un repo con `HEAD` sin commits o fuera de git se rechaza al abrir; si `repo_path` es una subcarpeta, el workspace es el repo entero.
