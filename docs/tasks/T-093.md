# T-093 — Keyboard and mouse without lag or failures

## Context

User's request (2026-11-15): that keyboard and mouse work on both machines without lag, without failures and respecting the screens. Goals and known failures in `docs/DESIGN.md` §7.1.

## Scope

1. **Measurement:** monotonic server timestamp on every `MotionDatagram` and on every key or click message; estimate of the clock offset with the heartbeats (round trip / 2); p50/p99/max histogram per link on the client, sent back to the server and published over IPC to the UI and to the log every 5 s.
2. **Latency bench:** test in `tandem-sim` (two agents over loopback, simulated capture and injection, 1000 motion events/s). In CI it only fails on a large regression (p99 > 20 ms) to avoid intermittent failures on the shared runners; the 1 ms p99 goal is checked with `cargo bench` / an `#[ignore = "bench"]` test locally.
3. **Hot path:** capture and datagram sending do not share a runtime with the clipboard or the IPC (dedicated thread or runtime); sending does not wait for QUIC *pacing* for the input datagrams (`TransportConfig` adjustment or immediate send, with a test); motion is sent as soon as it arrives, coalescing only what arrives while the previous send is still in progress.
4. **Known failures (with a test that fails first for each):**
   - Windows: the hook callback does no blocking work; the watchdog detects the silent loss of the hook and reinstalls it (already exists: verify with a timing test).
   - macOS: `kCGEventTapDisabledByTimeout` / `ByUserInput` reactivate the tap and are logged.
   - Stuck keys and buttons: when crossing machines, when the link drops, when switching links and when focus is lost, all are released on both sides.
   - Per-screen scale: T-092's declared arrangement carries a scale; the cursor keeps its physical speed when crossing between screens with different scales (property test).
   - Double click and drag between machines: a drag does not cross the edge with a button pressed (like Deskflow by default), configurable.
5. **Respect the screens:** the cursor never enters an area without a screen in the arrangement; corners and partial edges (screens of different height) with a property test.

## Acceptance criteria

- [x] p50/p99 latency visible in the log and over IPC.
- [x] Latency bench in CI, green and stable (no failures in 5 consecutive runs); local benchmark with p99 ≤ 1 ms documented in `## Notes`.
- [x] One test for each known failure of point 4, failing before the fix.
- [x] Geometry properties of point 5 with `proptest`.
- [x] Quality gate and CI green on the three platforms.

## Pending hardware verification

- [ ] Real latency over USB-C or Ethernet: p50 ≤ 1 ms, p99 ≤ 4 ms, in both directions (read in `InputStatus::latency` of both UIs and in the log: "input latency (capture → injection)").
- [ ] Real latency over Wi-Fi: p50 ≤ 5 ms, p99 ≤ 20 ms.
- [ ] An hour of normal use without stuck keys or a frozen cursor; unplug and plug the cable in the middle of a drag.
- [ ] Spanish/Latin American layout: the tilde-n key, dead keys, AltGr, in both directions.
- [ ] D7 with both machines: using the Mac's trackpad with the PC's cursor on top moves the keyboard to the Mac as soon as the PC has been still for 300 ms, and the other way round; with both in use at the same time it does not jump from one to the other.
- [ ] Windows: after forcing the loss of the hook (a debugger that freezes the hooks thread for longer than `LowLevelHooksTimeout`), the watchdog reinstalls it within one or two `hook_timeout` and the log says so.
- [ ] macOS: real `kCGEventTapDisabledByTimeout` / `ByUserInput` (Secure Input, a slow tap) reactivate the tap and are left in the log with their reason.
- [ ] Cross with Shift (or a click) pressed and release it on the other side: it is not left stuck on either machine (Windows and macOS).
- [ ] Monitors with different scales (the 4K at 150% and the MacBook's screen): the cursor feels at the same physical speed when crossing.
- [ ] A drag that reaches the edge does not cross; with `[input] drag_between_machines = true`, it does.

## Notes

- 2026-11-16 (v0.3): keyboard and mouse without an owner (DECISIONS D7): both machines capture and the one that receives physical input sends; include the arbitration here (DESIGN §7) and its tests. No USB-C cable today: real verification goes over Wi-Fi.
- 2026-11-17 (implementation):
  - **Measurement:** `tandem_input::session::latency` (log-linear histogram with error ≤ 1/32, NTP offset with the lowest-round-trip sample of the last 16, heartbeats with timestamp and echo). The client measures when injecting and every `SessionConfig::latency_every` (5 s) publishes, logs and sends `StreamMsg::Latency` to the server, which also publishes it. Both machines see it in `InputStatus::latency`, with the link (`Link`). Each event's timestamp is set on the capture thread (`Captured`, from `CaptureSink`: the tap thread on macOS and the hook's process thread on Windows), so the figure counts what the event waits in the channel and while the driver is busy (`la_latencia_incluye_la_espera_con_el_driver_ocupado`, which fails if it is stamped when taken out of the channel).
  - **D7 arbitration:** `tandem_input::session::Follow` + `ControlMsg::Focus` (request, handover and state with epoch). The hub no longer decides; capture always runs on both (DECISIONS, T-093 entries).
  - **Hot path:** the server and client drivers run on their own `current_thread` runtime (`tandem-input` thread); the clipboard, the IPC and the control network stay on the main one. Each captured batch goes out immediately as a datagram: `TransportConfig` was not touched (see DECISIONS).
  - **Known failures:**
    - macOS, stuck keys on the capturing machine: `soltar_lo_presionado_en_local_pasa_aunque_haya_grab` (`macos/capture/translate.rs`) failed before the fix (the release was swallowed); Windows already did it (`HookFilter`).
    - macOS, tap turned off: `tap_apagado_se_reactiva_y_se_registra` (reason separate, counted and logged with `warn`).
    - Windows: `el_paso_del_hook_no_bloquea_aunque_nadie_lea` and `el_watchdog_reinstala_a_tiempo_un_hook_perdido` (real clock). The watchdog takes one to two `hook_timeout`: during the first, a real input may still be that of the last event the hook saw (T-024's design, does not change).
    - Per-screen scale: `sin_perdidas_el_cliente_coincide_con_el_servidor_entre_escalas` failed before the fix (the logical delta of a datagram that went through two scales left the client in another place); now the delta travels in the client's native units. `la_velocidad_fisica_se_conserva_entre_escalas` covers the speed.
    - Drag: `un_arrastre_no_cruza_el_borde_salvo_que_se_permita`; configurable with `[input] drag_between_machines`.
    - Keys released when the link drops or changes and when sending stops (D7): the tests in `tandem-input/tests/session.rs` and `tandemd/tests/input.rs` (the one that stops sending returns the capture and the other releases everything).
  - **Respect the screens:** `un_paseo_nunca_sale_de_las_pantallas_y_cruza_solo_por_bordes_expuestos` (geometry) and `el_cursor_inyectado_nunca_sale_de_las_pantallas` (full session).
  - **Bench:** `crates/tandem-sim/tests/latency.rs`. In CI, up to three batches of 1000 movements at 1000/s: it fails if all three exceed 20 ms p99. Five consecutive runs in WSL (debug, with other agents compiling): p99 from 0.73 to 13.2 ms, all green.
  - **Local benchmark** (`cargo test -p tandem-sim --release --test latency -- --ignored --nocapture`, 5000 movements, loopback, Ryzen 7 9800X3D in WSL2): with the machine idle p50 0.27–0.30 ms and p99 0.43–0.66 ms (≤ 1 ms). With other agents compiling (load 7–14 on 8 cores) isolated scheduler pauses of 7–15 ms appear that raise p99 to 2.7–8 ms; they look like a single pause that decays by 1 ms over the following events, not like a periodic pattern of the engine.
  - **T-101's Qos:** `feed_qos` (`tandemd/src/input/mod.rs`) feeds the active path's `Qos` (`agent.link_qos().get(link).record_input_latency(..)`) on both machines: the one that injects does it with each sample, and the one that captures with the p99 of each window that the other reports to it (every 5 s, more spaced than the guardian's window). Tested by `the_input_latency_feeds_the_link_qos_on_both_machines`, with the new `Qos::input_p99` in `tandem-link`.
  - **Two-agent tests that hung with the machine loaded (cause confirmed in the review of #78):** `free_port()` chose a port and released it; another suite running at the same time took it, and the agent silently moved to a fixed fallback port (52100…) while the other kept dialing the old one. With fixed identities, the other agent could even connect to the agent of *another* suite, with the same key: session up on both, but the cursor crossed to the wrong machine (what was seen in the bench: "the cursor did not cross to B" with both sessions active). Fix: the harnesses start without fallback ports (`fallback_ports` empty; also the binary with `--sim-backends`), a taken port fails right away and `tandemd::start_pair!` / `start_solo!` (`tandemd::test_ports`) choose others. The `tandem-sim` bench also uses fresh identities for each pair. Test: `a_port_taken_before_starting_fails_fast_and_the_pair_picks_new_ones` (`tandemd/tests/input.rs`) and the `test_ports` unit test. Harnesses moved to the same scheme: `input`, `network`, `modules`, `wizard`, `pairing`, `environments` and `tandem_sim::InputPair`. Left with staggered startup on purpose (`power_on_waits_for_the_pc_agent`, `a_change_made_while_the_other_was_away_arrives_on_reconnect`): the second agent, if it finds its port taken, fails right away with a message instead of hanging. `two_processes.rs` restarts processes on fixed ports: without a fallback it fails right away, but does not retry. The pairing port (`port + 1`) in `pairing.rs` has the same race and is not covered here. There was a second cause, found in T-101's review: the server opened the session before knowing the other machine's OS. When its capabilities arrived the capture was rebuilt, and a crossing already made was lost. Now the session waits for that data (`the_input_session_waits_for_the_other_machines_os` fails without the fix). There was a third cause, seen in the `tandem-sim` bench as "the cursor did not cross to B" with both sessions active (1 in 9 isolated runs). When rebuilding the capture, the server read the geometry and then subscribed to it. If the other's screens arrived in between (they arrive together with its capabilities, right when it is rebuilt), the change was marked as seen, and the session stayed without the other machine until the next change. Now it subscribes first; after the fix, 20 of 20 runs passed. This race has no test of its own that forces it: the gap is microseconds. No maximum time was raised; `within` says on which line it waited and `TANDEM_TEST_LOG` shows the agents' log.
  - **Desk in memory before `tandem.toml` (failure of `a_change_made_while_the_other_was_away_arrives_on_reconnect` on macOS):**
    - Cause: `learn_machines` (on getting to know each other, when the two machines and the default scenes are noted) and `set_desk` published the new desk in memory and only afterwards saved it and bumped its version.
    - Effect: during that gap, the UI, the other machine and the tests saw a desk that was not yet in the file. The test compared the file with memory and sometimes found the file without the machines. It comes from `develop`.
    - Fix: the desk is only published after saving it (`Agent::commit_desk`).
    - Test: `the_desk_in_memory_is_never_ahead_of_tandem_toml` failed on the first run before the fix; afterwards 10 of 10 passed, plus 40 of 40 of the original test under load.
  - **UI:** `InputStatus` carries `latency` (with `#[serde(default)]`); in `apps/tandem-ui/src-tauri` only the field was added to a test literal. Showing it belongs to T-118 (Network screen).
