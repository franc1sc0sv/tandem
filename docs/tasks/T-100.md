# T-100 — Escenas

## Context

DECISIONS D6; DESIGN §5. Los modos Solo Mac / Compartido / Solo Windows desaparecen.

## Scope

1. Modelo `Scene { id, name, icon, monitors: Vec<(MonitorId, Machine)>, layout: Option<Layout>, require_on: Option<Machine>, shortcut }` dentro del `Desk`.
2. Escenas por omisión al emparejar: «Trabajo» (todo compartido), «Solo <A>», «Solo <B>», con los nombres reales de las máquinas.
3. Aplicar escena = transacción del orquestador: encender si hace falta → (monitores: paso abstracto `SwitchMonitor` que T-111 conecta a hardware; aquí con doble) → acomodo → geometría. Vuelta atrás si falla un paso. Progreso por IPC paso a paso (para `F-Transacciones`).
4. IPC: crear, editar, borrar, aplicar; escena activa en el estado; atajo global por escena.
5. Quitar el código de modos y sus textos de la UI vieja.

## Acceptance criteria

- [x] Escenarios de `tandem-sim`: aplicar escena con éxito; falla en el paso de monitor → vuelta atrás completa; la otra máquina apagada → se enciende primero.
- [x] Pruebas unitarias del modelo y de las escenas por omisión.
- [x] Puerta de calidad y CI en verde.

## Notes

- **Modelo** (`tandem-core/src/scene.rs`): `Scene { id, name, icon, monitors: Vec<(MonitorId, Machine)>, layout: Option<Arrangement>, require_on: Option<Machine>, shortcut }`. El `Layout` de la tarea es el `Arrangement` del puesto (D18). Las máquinas que necesita una escena son `require_on` ∪ las que muestra algún monitor ∪ las dos si tiene acomodo (un acomodo relaciona a las dos): así «Trabajo» («todo compartido») enciende a la otra aunque `require_on` sea una sola máquina.
- **Por omisión** al conocerse las dos máquinas (`learn_machines`), si el puesto no tiene escenas: «Trabajo» (con el acomodo de ese momento, ⌃⌥1), «Solo <A>» (⌃⌥2) y «Solo <B>» (⌃⌥3). No disparan el aviso «Cambiado desde X». Renombrar una máquina renombra su «Solo …» si el usuario no lo cambió.
- **Pasos** nuevos de `Step`: `ShowMachine { monitor, machine }` (el paso abstracto de la tarea; se llama así porque `SwitchMonitor` ya es el paso real de T-110 con la entrada; T-111 traduce uno al otro), `Arrange { layout }` y `Geometry`. Los hace la máquina que aplica la escena (`Orchestrator::run_scene` con `SceneSteps`); la otra nunca los hace a pedido. Vuelta atrás con `Executor::undo` de T-110: monitores y acomodo vuelven a lo de antes; la energía no se deshace (como siempre). La UI ve cada paso deshecho con `TxnEvent::StepUndone`.
- **Hasta T-111** el monitor y la geometría van detrás de `SceneBackend`: en el agente real `NoSceneMonitors` (una escena con monitores falla en el primero, sin tocar nada; la geometría ya la recalcula el motor de entrada al cambiar puesto y estado); en `tandem-sim`, `SceneScreens` con fallos del `FaultPlan`.
- **IPC**: crear, editar y borrar son parches del puesto (`DeskPatch::AddScene`, `EditScene`, `DeleteScene`; viajan y se deshacen como el resto, D5); aplicar es `UiCommand::ApplyScene { id }`. La escena activa es `State.scene`: se anota al terminar bien y se borra si la escena desaparece o se apaga una máquina que necesita.
- **Atajos globales**: `SceneShortcuts` mira las teclas físicas en la captura de la máquina que tiene el teclado (funciona con el cursor en cualquiera) y aplica la escena; un atajo repetido (con otra escena o con el de bloqueo) se rechaza al validar el puesto.
- **Modos**: el código ya se había ido con T-092; quedaban textos en comentarios (bandeja, configuración, pruebas) y se cambiaron.
- Protocolo v23 (después de T-105, T-101 y T-122): escenas completas en el puesto, `State.scene`, pasos de escena, `StepUndone`, `ApplyScene`.
- **Revisión de #82**: escenario de dos agentes que crea, edita y borra escenas (también la activa); los parches de escena entran en las propiedades de D5; un `tandem.toml` de T-099 ya emparejado (sin la clave `scenes`) recibe las escenas por omisión una sola vez al cargarlo, como cambio de esta máquina, y borrarlas todas deja `scenes = []`; la escena por omisión cuyo atajo choca con el de bloqueo (u otra) queda sin atajo y el puesto se valida antes de agregarlas. La vigilancia del par ahora mira el enlace antes que el estado (`select!` con `biased`): con los dos avisos a la vez, una máquina recién encendida podía darse por perdida (lo destapó el escenario de «Trabajo», intermitente).
