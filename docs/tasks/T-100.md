# T-100 — Scenes

## Context

DECISIONS D6; DESIGN §5. The Mac only / Shared / Windows only modes disappear.

## Scope

1. `Scene { id, name, icon, monitors: Vec<(MonitorId, Machine)>, layout: Option<Layout>, require_on: Option<Machine>, shortcut }` model inside the `Desk`.
2. Default scenes on pairing: "Work" (everything shared), "<A> only", "<B> only", with the machines' real names.
3. Applying a scene = orchestrator transaction: power on if needed → (monitors: abstract `SwitchMonitor` step that T-111 connects to hardware; here with a double) → arrangement → geometry. Rollback if a step fails. Progress over IPC step by step (for `F-Transactions`).
4. IPC: create, edit, delete, apply; active scene in the state; global shortcut per scene.
5. Remove the modes code and its texts from the old UI.

## Acceptance criteria

- [x] `tandem-sim` scenarios: applying a scene successfully; failure at the monitor step → full rollback; the other machine off → it is powered on first.
- [x] Unit tests of the model and of the default scenes.
- [x] Quality gate and CI green.

## Notes

- **Model** (`tandem-core/src/scene.rs`): `Scene { id, name, icon, monitors: Vec<(MonitorId, Machine)>, layout: Option<Arrangement>, require_on: Option<Machine>, shortcut }`. The task's `Layout` is the desk's `Arrangement` (D18). The machines a scene needs are `require_on` ∪ those shown by some monitor ∪ both if it has an arrangement (an arrangement relates the two): so "Work" ("everything shared") powers on the other even if `require_on` is a single machine.
- **By default** when the two machines get to know each other (`learn_machines`), if the desk has no scenes: "Work" (with the arrangement of that moment, ⌃⌥1), "<A> only" (⌃⌥2) and "<B> only" (⌃⌥3). They do not trigger the "Changed from X" notice. Renaming a machine renames its "… only" if the user did not change it.
- New `Step`s: `ShowMachine { monitor, machine }` (the task's abstract step; it is called that because `SwitchMonitor` is already T-110's real step with the input; T-111 translates one into the other), `Arrange { layout }` and `Geometry`. They are done by the machine that applies the scene (`Orchestrator::run_scene` with `SceneSteps`); the other never does them on request. Rollback with T-110's `Executor::undo`: monitors and arrangement go back to what they were; power is not undone (as always). The UI sees each undone step with `TxnEvent::StepUndone`.
- **Until T-111** the monitor and the geometry go behind `SceneBackend`: in the real agent `NoSceneMonitors` (a scene with monitors fails on the first one, touching nothing; the geometry is already recalculated by the input engine when the desk and state change); in `tandem-sim`, `SceneScreens` with faults from the `FaultPlan`.
- **IPC**: create, edit and delete are desk patches (`DeskPatch::AddScene`, `EditScene`, `DeleteScene`; they travel and are undone like the rest, D5); applying is `UiCommand::ApplyScene { id }`. The active scene is `State.scene`: it is noted when finishing well and cleared if the scene disappears or a machine it needs is turned off.
- **Global shortcuts**: `SceneShortcuts` watches the physical keys in the capture of the machine that has the keyboard (works with the cursor on either) and applies the scene; a repeated shortcut (with another scene or with the lock one) is rejected when validating the desk.
- **Modes**: the code had already gone with T-092; texts remained in comments (tray, configuration, tests) and were changed.
- Protocol v23 (after T-105, T-101 and T-122): complete scenes in the desk, `State.scene`, scene steps, `StepUndone`, `ApplyScene`.
- **Review of #82**: two-agent scenario that creates, edits and deletes scenes (also the active one); the scene patches enter D5's properties; a T-099 `tandem.toml` already paired (without the `scenes` key) receives the default scenes only once on loading, as a change by this machine, and deleting them all leaves `scenes = []`; the default scene whose shortcut clashes with the lock one (or another) is left without a shortcut and the desk is validated before adding them. The peer watch now looks at the link before the state (`select!` with `biased`): with both notices at once, a freshly powered-on machine could be taken as lost (uncovered by the "Work" scenario, intermittent).
