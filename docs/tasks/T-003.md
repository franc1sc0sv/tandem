# T-003 — Identity and pairing

## Scope

In `tandem-link` (module `identity`): one Ed25519 key per machine, persisted in a file with 0600 permissions for now (Keychain/DPAPI in a later task).
Pairing by numeric comparison with commitment (like Bluetooth SSP or ZRTP's SAS): each side contributes a 32-byte nonce; the initiator sends its key first and `commit = SHA-256("tandem-pairing-commit-v1"‖pub_i‖nonce_i)`, the responder sends its key and `nonce_r`, and the initiator reveals `nonce_i`, which the other side checks against the commitment. Each side shows the 6-digit code `SHA-256("tandem-pairing-v2"‖min(pub)‖max(pub)‖nonce_i‖nonce_r)[..8] mod 10^6`; once both sides confirm, the peer's pubkey is saved in a trust store.
Self-signed certificate (rcgen) derived from the key, for use in QUIC with pinning.

## Acceptance criteria

- [x] The 6-digit code is the same on both sides and changes if either key or either nonce changes (test).
- [x] A commitment that does not match the key or the revealed nonce is rejected with `CommitMismatch` (test).
- [x] The trust store persists and reloads; an untrusted peer is rejected.
- [x] No `unwrap()` outside tests.

## Notes

- Implemented in `crates/tandem-link/src/identity/`: `Identity` (Ed25519 key, 32-byte file with 0600 and atomic write; on Unix it is rejected if others can read it), `PairingInitiator`/`PairingResponder`/`Pairing` (the three messages `PairingOffer`, `PairingAnswer` and `PairingReveal`; the peer confirms by sending the code it saw, but that only coordinates the close: security comes from the user's comparison), `TrustStore` (versioned TOML, `verify` returns `Untrusted`) and `Identity::tls_certificate` (rcgen, self-signed, fixed name `tandem` for T-004's pinning).
- On Windows the file has no special permissions beyond the profile's ACLs; real protection arrives with DPAPI/Keychain in the later task.
- The original scope derived the code from the two keys only. That let a man-in-the-middle brute-force a key of their own that gave the same code on both screens (PR #4's review found a collision in 1.5 s). It was changed to the commitment protocol: the attacker has to fix their key and their nonce before knowing the nonce that decides the code on the other side, so they succeed with probability 10^-6 per attempt. Message serialization and transport are left for T-004.
