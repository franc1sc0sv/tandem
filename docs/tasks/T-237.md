# T-237 — One-way reachability must still give a working link

## Context

Found in the cable run of 2026-11-18 (`docs/reports/hw-2026-11-18-cable.md`). The Mac had its firewall on with stealth mode, so inbound UDP to the unsigned test `tandemd` was dropped silently. The Mac dialed the PC over USB4 and its checks passed (pair, ping 1 ms, tunnels served by the PC agent). The PC agent never considered the peer connected: `GetPeer` never reported it, ping said "no link sees the other machine", tunnels said "the other machine is not connected", and the input session never started.

The PC log showed repeated `connection from the other agent from=[::ffff:169.254.93.252%21]:47871` followed by `connection with the other agent ended: connection: closed by peer: 0` or `read of the control stream: connection lost`, while its own link manager kept `candidates=[Usb4 169.254.93.252:47871]` and never managed to dial.

## Root cause

- A side only considered the peer reachable over connections its own link manager dialed. Connections the other agent opened were served (pings, steps) but never used as this side's path, and the dialer did not serve streams opened over its own connections, so the side that could not dial had no way to talk.
- Every mDNS change (for example a scoped IPv6 link-local appearing or leaving) rebuilt the link manager even when the links it follows stayed the same, dropping every healthy connection. The other side sees each rebuild as `closed by peer: 0` and a new connection right after. The Mac logs were not available, so this is the likely cause of the churn the PC saw, not a confirmed one.

## Fix

- The dialing side serves the streams the other agent opens over its connections (`peer::accept_streams` on dialed connections too).
- For each path, the prober first adopts a live, authenticated connection the paired peer opened over it (same IP, else same kind; the newest wins) and only dials when there is none. One that cannot take a session in half the connect timeout is closed and the side dials instead.
- A path the peer reached this side over that no candidate covers enters the link manager.
- Tie-breaking when both dial: each side keeps the session it already has; nothing is closed because of a duplicate, so the link does not flap.
- `supervise` no longer rebuilds the manager when a discovery change leaves the same links (same kinds and addresses after relabelling). Its log prints the relabelled links, not the declared kinds.
- Unpairing leaves the connection that carries the `Unpaired` notice open for a short while, since closing it drops unsent data. With adoption that connection can be the one the other side dialed.
- Test hook: `NetOptions::dial = false` plays a peer whose firewall drops everything this side sends.

## Criteria

- [x] Failing tests first: two real agents over loopback with one direction blocked (`crates/tandemd/tests/network.rs`) fail without the fix (adoption turned off: timeout waiting for the peer) and pass with it, in both directions.
- [x] The side that cannot dial shows the peer connected over the path, the wizard ping answers, and steps reach the other machine in both directions.
- [x] A peer trusted without a configured address links over the path the other agent came in on.
- [x] With both directions open, the peer status does not change once the link is up (no flapping).
- [x] Unit tests: inbound connection lookup (IP, then kind, newest, live only, only the paired key, never a dialed one), IPv4-mapped addresses dialed back as IPv4, and rebuilding only when the links change.
- [x] Quality gate passes.

## Notes

- `data cap link=Some(Wifi)` and the `the links with the peer changed next=[LinkCandidate { kind: Wifi, ... }]` log for the cable address: PR #161 (T-223, merged into `develop` while this task was open; this branch is rebased on it) does not cover them. It deduplicates candidates of the same kind after relabelling. The log printed the declared kinds before relabelling, and now prints the relabelled links. The manager itself already used `Usb4`. The cap label is the worse of the two ends' classifications (T-094), so `Wifi` there most likely means the Mac classified its Thunderbolt Bridge as Wi-Fi, or fell back to the declared kind. That needs the Mac to check (see the pending list).
