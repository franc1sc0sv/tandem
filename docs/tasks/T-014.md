# T-014 — MonitorSwitcher and display step executor

## Scope

`MonitorSwitcher` trait (DESIGN §8) with backends: `ddc-windows` (uses T-010 and the DDC profile from the config), `manual` (asks the user through the UI and waits for confirmation). On the Mac, `SwitchInput` is forwarded to the PC.
Implement in T-008's Executor the steps `SwitchInput`, `Attach`, `Detach`, `SetBuiltin`, delegating to the platform backends (those that do not exist yet return `not implemented`).

## Acceptance criteria

- [x] Routing tests with simulated backends: on the Mac, SwitchInput goes to the PC.
- [x] The manual backend emits a UI event and waits for confirmation (test).

## Notes

- `tandem-display::switcher`: `MonitorSwitcher` trait (async, cancelled by dropping the future, which is how the step's maximum time cuts it off) with `SwitchRequest { monitor, to, input }`. Backends:
  - `DdcSwitcher`: opens the bus on each switch (the monitor list can change and handles do not survive every topology change, S3), finds the monitor by `edid_model` (with no match or several it writes nothing), writes `0x60` with the code from the config's `ddc` profile, with 3 retries, outside the runtime (`spawn_blocking`). `DdcSwitcher::windows()` uses T-010's `WindowsDdc`. No automatic return: the safety net is the transaction's rollback.
  - `ManualSwitcher`: publishes `ManualEvent::Requested` (monitor, label, machine and input) and waits for `answer(id, done)`; `done = false` fails the step. With no UI subscribed it fails right away instead of waiting for the cap. When finished (answered, expired or cancelled) it publishes `Closed` so the UI removes the notice.
  - `PerMonitor`: monitors with a `ddc` profile in the config go through DDC, the rest manually (today the 32", until T-050).
- `tandem-display::desktop`: `DesktopControl` trait (`attach`, `detach`, `set_builtin`). `TopologyDesktop` implements it over T-011's `DisplayTopology`, finding the monitor by `edid_model`; on the PC (Windows) it runs over `WindowsTopology`. The Mac is left without a desktop backend until T-012 («not implemented»).
- Risk inherited from T-011: `dxva2` does not see deactivated monitors, so bringing a monitor to the PC needs "activate → DDC", and `tandem-core`'s plan today sends `SwitchInput` before `Attach`. With a monitor outside the Windows desktop, DDC would answer «no connected monitor matches» and the transaction would roll back. The plan's order was not changed (it is design); it is reported.
- `tandemd::display::DisplaySteps` (implements `LocalSteps`): `SwitchInput` only on the PC (on the Mac it answers that the PC switches the inputs; the orchestrator already sends it there), `Attach`/`Detach` on the step's machine and `SetBuiltin` on the Mac, through `DesktopControl` in `spawn_blocking`. What has no backend answers «not implemented»; `PowerOnPc`, `PowerOffPc` and `UpdateInputGeometry` go to `with_others` (today `Unimplemented`, for T-030 and the input engine). `Agent::with_platform` (used by `main`) assembles DDC + manual on the PC; on Linux/macOS DDC answers «DDC/CI is not available on this platform».
- Protocol: `AgentToUi::ManualSwitch(ManualSwitchEvent::{Requested, Closed})`, `UiCommand::AnswerManualSwitch { id, done }` and `Reply::Done` (variants added at the end, compatible with the existing messages). IPC forwards the requests to the UI of the machine that does the switch (the PC).
- The user has `step_timeout_secs` (10 s by default) to switch by hand and confirm; if that is not enough, raise it in `[orchestrator]`.
- Tests: unit tests of each backend (`FakeDdc` shared with `SharedFakeDdc`, paused clock for the manual backend's expiry), of `DisplaySteps` (Mac → PC routing with the orchestrator, «not implemented», desktop) and integration with real QUIC (`tests/orchestrator.rs`): the Mac's UI asks for Windows only, the PC switches the 34" through simulated DDC and the 32" by hand confirmed from its UI; if the user rejects the manual switch, everything rolls back and the 34" returns to HDMI.
