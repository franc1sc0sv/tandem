# T-104 — Procesos remotos

## Contexto

DESIGN §8; mockups `V3-Computo` (lista de procesos corriendo + salida del seleccionado) y `F-ClaudeMCP`.

## Alcance

1. `exec { tunnel, cmd, args, shell: Option<EnvId>, cwd, env }` → `process_id`. Varios procesos por túnel en paralelo.
2. Backends detrás de un trait `Spawner`: Windows (`CreateProcess` con job object para matar el árbol; PowerShell, cmd, `wsl.exe -d <distro>`, `docker exec`), macOS/Unix (`posix_spawn`/`tokio::process`, grupo de procesos). Doble de prueba.
3. `output { process, from_byte }` en vivo (stdout y stderr marcados), `kill { process }` (árbol completo), código de salida y duración.
4. Privilegios (A7): el proceso hereda los del agente. El instalador de Windows registra el agente como tarea programada «con los privilegios más altos» (actualizar el instalador y `docs/dev/install-windows.md`).
5. Lista de procesos **corriendo** por túnel para la UI (los terminados salen de la lista de la UI; quedan consultables por MCP 10 min).

## Criterios de aceptación

- [ ] Pruebas en las tres plataformas (CI) con el backend real lanzando procesos simples (`echo`, `sleep`, salida grande de 10 MB) y matando árboles de procesos.
- [ ] Escenario de dos agentes con el doble: 5 procesos a la vez, salida intercalada correcta, kill de uno no afecta a los demás.
- [ ] Puerta de calidad y CI en verde.

## Verificación en hardware pendiente

- [ ] Desde WSL (PC) abrir túnel a la Mac por Wi-Fi y correr `cargo test` de un repo pequeño; y desde la Mac a la PC en PowerShell y en WSL.
- [ ] Proceso elevado en Windows: `net session` responde sin error de acceso.
