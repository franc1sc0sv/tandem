# T-104 — Procesos remotos

## Context

DESIGN §8; mockups `V3-Computo` (lista de procesos corriendo + salida del seleccionado) y `F-ClaudeMCP`.

## Scope

1. `exec { tunnel, cmd, args, shell: Option<EnvId>, cwd, env }` → `process_id`. Varios procesos por túnel en paralelo.
2. Backends detrás de un trait `Spawner`: Windows (`CreateProcess` con job object para matar el árbol; PowerShell, cmd, `wsl.exe -d <distro>`, `docker exec`), macOS/Unix (`posix_spawn`/`tokio::process`, grupo de procesos). Doble de prueba.
3. `output { process, from_byte }` en vivo (stdout y stderr marcados), `kill { process }` (árbol completo), código de salida y duración.
4. Privilegios (A7): el proceso hereda los del agente. El instalador de Windows registra el agente como tarea programada «con los privilegios más altos» (actualizar el instalador y `docs/dev/install-windows.md`).
5. Lista de procesos **corriendo** por túnel para la UI (los terminados salen de la lista de la UI; quedan consultables por MCP 10 min).

## Acceptance criteria

- [x] Pruebas en las tres plataformas (CI) con el backend real lanzando procesos simples (`echo`, `sleep`, salida grande de 10 MB) y matando árboles de procesos. (`crates/tandem-tunnel/tests/system.rs`, con el binario de prueba `tandem-tunnel-probe` como proceso igual en los tres sistemas.)
- [x] Escenario de dos agentes con el doble: 5 procesos a la vez, salida intercalada correcta, kill de uno no afecta a los demás. (`crates/tandemd/tests/processes.rs`, dos `tandemd` por QUIC con `start_pair!`; y `crates/tandem-tunnel/tests/processes.rs`, en memoria.)
- [x] Puerta de calidad y CI en verde.

## Notes

Hecho:

- Protocolo v32 (v26 es de T-093, v28 de T-102, v29 de T-111, v30 de T-128 y v31 de T-106, que entraron antes): `TunnelUp::{Exec, Kill}`, `TunnelDown::{Started, Killed, Process}`, `UiCommand::{Exec, Kill, Output, GetProcesses}`, `Reply::{Process, Processes, Output}`, y `TunnelView { tunnel, running }` en lugar de `Tunnel` dentro de `ProjectTunnels` (la UI recibe los procesos corriendo de cada túnel). `ExecSpec.shell` es el id de un entorno de `tandem-env` (`zsh`, `pwsh`, `cmd`, `wsl:<distro>`) o `docker:<contenedor>`.
- `tandem-tunnel::process`:
  - `launch`: de un `exec` a la orden concreta, portable y probado para los dos sistemas (shells de login en Unix, `-EncodedCommand` en PowerShell, `cmd /d /s /c` con línea cruda, `wsl.exe -d <distro> --cd … --exec sh -lc`, `docker exec -i`), con citado propio y pruebas de propiedades.
  - `Spawner` / `Child`: lo que depende del sistema. `SystemSpawner` es el real (`tokio::process`; en Unix un grupo de procesos por proceso y `killpg`; en Windows un objeto de trabajo y `TerminateJobObject`). `FakeSpawner` es el doble: la prueba escribe la salida, termina el proceso y ve si lo mataron. El stdin de todo proceso va cerrado.
  - Cada proceso son dos flujos del túnel (stdout, stderr) con el búfer circular de siempre, así que sobrevive al enlace sin código aparte; el origen se entera de su estado por el canal de datos (`TunnelDown::Process`). `Host::set_spawner` cambia el lanzador (el real por omisión).
  - Los terminados salen de `TunnelView.running` pero quedan consultables (`processes`, `output`) `linger` (10 min) en los dos lados; pasado eso se olvidan con sus flujos.
  - Un proceso que termina dejando un descendiente con la salida abierta figura terminado, pero su salida sigue hasta que el descendiente la cierre; `kill` o cerrar el túnel matan todo el grupo. `release` marca el árbol como terminado cuando ya no queda nada, para no matar un pid que el sistema reutilizó.
  - Cerrar el túnel mata todos los árboles (y ningún proceso nuevo entra: `Table::insert` revisa el túnel con el candado de la tabla).
- `Origin::{exec, kill, processes, output, views}`, `Tunnels::{processes, output}` (del espejo si el túnel lo abrió esta máquina; si no, de los flujos propios, para que la UI de la destino también vea la salida).
- `tandemd`: `UiCommand::Exec` y `Kill` solo desde un cliente (`Peer::Client`); `GetProcesses` y `Output` también las puede pedir la UI (solo lectura, D9). `Output` devuelve hasta 400 KiB por flujo y trae `from`/`next`: si lo pedido ya se descartó, `from` va más adelante.
- Privilegios (A7): el proceso hereda los del agente; nada los cambia. El instalador de Windows (`tandemd --install`) registra, con administrador, la tarea programada `Tandem\tandemd` con `RunLevel = HighestAvailable` (XML propio: sin límite de tiempo y con batería, `UserId` obligatorio) y quita el valor de `Run`, solo si el ejecutable y su carpeta solo los escriben administradores (`PathAcl`, `WinAcl` lee la ACL); si no, o sin administrador, deja la clave `Run` y avisa que los procesos no estarán elevados. La lógica va detrás de `Scheduler` y `PathAcl` con dobles en memoria; `HighestTask` usa la API COM del Programador de tareas (sin archivo del XML). En Windows los procesos nacen suspendidos, entran al job object y se reanudan. `docs/dev/install-windows.md` y `tools/windows/installer/test-installer.ps1` actualizados (el CI corre elevado y espera la tarea).

Para las tareas siguientes:

- T-108 (MCP y CLI): `exec`, `kill`, `output` y `tunnels` salen de `UiCommand::{Exec, Kill, Output, GetProcesses, GetTunnels}`; `output` no espera: se lee de nuevo desde `next` (o se suscribe a `AgentToUi::Tunnels` para saber cuándo termina un proceso).
- La sesión de Tauri todavía ignora `Reply::{Process, Processes, Output}` y el aviso de túneles no pinta los procesos: la pantalla Túneles es de otra tarea.
