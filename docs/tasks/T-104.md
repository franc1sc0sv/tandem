# T-104 — Remote processes

## Context

DESIGN §8; mockups `V3-Compute` (list of running processes + output of the selected one) and `F-ClaudeMCP`.

## Scope

1. `exec { tunnel, cmd, args, shell: Option<EnvId>, cwd, env }` → `process_id`. Several processes per tunnel in parallel.
2. Backends behind a `Spawner` trait: Windows (`CreateProcess` with a job object to kill the tree; PowerShell, cmd, `wsl.exe -d <distro>`, `docker exec`), macOS/Unix (`posix_spawn`/`tokio::process`, process group). Test double.
3. Live `output { process, from_byte }` (stdout and stderr marked), `kill { process }` (whole tree), exit code and duration.
4. Privileges (A7): the process inherits the agent's. The Windows installer registers the agent as a scheduled task "with the highest privileges" (update the installer and `docs/dev/install-windows.md`).
5. List of **running** processes per tunnel for the UI (finished ones leave the UI list; they stay queryable through MCP for 10 min).

## Acceptance criteria

- [x] Tests on the three platforms (CI) with the real backend launching simple processes (`echo`, `sleep`, 10 MB large output) and killing process trees. (`crates/tandem-tunnel/tests/system.rs`, with the `tandem-tunnel-probe` test binary as the same process on all three systems.)
- [x] Two-agent scenario with the double: 5 processes at once, correct interleaved output, killing one does not affect the others. (`crates/tandemd/tests/processes.rs`, two `tandemd` over QUIC with `start_pair!`; and `crates/tandem-tunnel/tests/processes.rs`, in memory.)
- [x] Quality gate and CI green.

## Notes

Done:

- Protocol v32 (v26 is T-093's, v28 T-102's, v29 T-111's, v30 T-128's and v31 T-106's, which came in earlier): `TunnelUp::{Exec, Kill}`, `TunnelDown::{Started, Killed, Process}`, `UiCommand::{Exec, Kill, Output, GetProcesses}`, `Reply::{Process, Processes, Output}`, and `TunnelView { tunnel, running }` instead of `Tunnel` inside `ProjectTunnels` (the UI receives each tunnel's running processes). `ExecSpec.shell` is the id of a `tandem-env` environment (`zsh`, `pwsh`, `cmd`, `wsl:<distro>`) or `docker:<container>`.
- `tandem-tunnel::process`:
  - `launch`: from an `exec` to the concrete command, portable and tested for both systems (login shells on Unix, `-EncodedCommand` in PowerShell, `cmd /d /s /c` with a raw line, `wsl.exe -d <distro> --cd … --exec sh -lc`, `docker exec -i`), with its own quoting and property tests.
  - `Spawner` / `Child`: what depends on the system. `SystemSpawner` is the real one (`tokio::process`; on Unix one process group per process and `killpg`; on Windows a job object and `TerminateJobObject`). `FakeSpawner` is the double: the test writes the output, ends the process and sees whether it was killed. Every process's stdin is closed.
  - Each process is two tunnel flows (stdout, stderr) with the usual circular buffer, so it survives the link without separate code; the origin learns its state over the data channel (`TunnelDown::Process`). `Host::set_spawner` changes the launcher (the real one by default).
  - Finished ones leave `TunnelView.running` but stay queryable (`processes`, `output`) for `linger` (10 min) on both sides; after that they are forgotten along with their flows.
  - A process that ends leaving a descendant with the output open appears finished, but its output continues until the descendant closes it; `kill` or closing the tunnel kills the whole group. `release` marks the tree as finished when nothing is left, so as not to kill a pid the system reused.
  - Closing the tunnel kills all the trees (and no new process enters: `Table::insert` checks the tunnel with the table's lock).
- `Origin::{exec, kill, processes, output, views}`, `Tunnels::{processes, output}` (from the mirror if the tunnel was opened by this machine; otherwise, from its own flows, so the target's UI also sees the output).
- `tandemd`: `UiCommand::Exec` and `Kill` only from a client (`Peer::Client`); `GetProcesses` and `Output` can also be requested by the UI (read-only, D9). `Output` returns up to 400 KiB per flow and carries `from`/`next`: if what was requested was already discarded, `from` is further ahead.
- Privileges (A7): the process inherits the agent's; nothing changes them. The Windows installer (`tandemd --install`) registers, with administrator, the scheduled task `Tandem\tandemd` with `RunLevel = HighestAvailable` (own XML: no time limit and on battery, mandatory `UserId`) and removes the `Run` value, only if the executable and its folder can only be written by administrators (`PathAcl`, `WinAcl` reads the ACL); otherwise, or without administrator, it leaves the `Run` key and warns that processes will not be elevated. The logic goes behind `Scheduler` and `PathAcl` with in-memory doubles; `HighestTask` uses the Task Scheduler COM API (no XML file). On Windows processes are born suspended, enter the job object and are resumed. `docs/dev/install-windows.md` and `tools/windows/installer/test-installer.ps1` updated (the CI runs elevated and expects the task).

For the following tasks:

- T-108 (MCP and CLI): `exec`, `kill`, `output` and `tunnels` come from `UiCommand::{Exec, Kill, Output, GetProcesses, GetTunnels}`; `output` does not wait: it is read again from `next` (or it subscribes to `AgentToUi::Tunnels` to know when a process ends).
- The Tauri session still ignores `Reply::{Process, Processes, Output}` and the tunnels notice does not draw the processes: the Tunnels screen belongs to another task.
