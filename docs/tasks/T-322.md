# T-322 — `a_local_setting_moved_to_the_desk_does_not_leave_the_machines_apart` still flakes (a different wait than T-235)

## Context

Failure found by the acceptance agent, part C, round 6 (2026-11-19, `origin/develop` 9fe53be). See `docs/reports/acceptance-2026-11-19-c6.md`. T-235 fixed a different step of the same test (`until_same_desk` already true before the merge); this is the wait before it.

## Failure

G11. `cargo test --workspace` failed on the first run on a clean checkout of `develop`:

```
test a_local_setting_moved_to_the_desk_does_not_leave_the_machines_apart ... FAILED
thread 'a_local_setting_moved_to_the_desk_does_not_leave_the_machines_apart' panicked at crates/tandemd/tests/network.rs:45:23:
```

Line 1003 is `within(on_a.wait_for(off)).await.unwrap()`: agent A (the one with no legacy `[input] clipboard`) never sees `modules.b.clipboard == false` in its desk within `within`'s 20 s, although agent B (`clipboard = false` in the pre-T-099 `[input]`) has it off. Other tests of the binary finish in 1 to 2 s, so this is a lost update, not a slow one.

Reproduction: the machine was loaded (load average 17 to 23 on 8 CPUs, other acceptance builds running). Running the test alone 15 times with `cargo test -p tandemd --test network a_local_setting_moved` under that load failed 1 of 15, with the same panic. The unloaded rerun of the whole workspace (`--no-fail-fast`) passed: 1623 passed, 0 failed, 11 ignored. CI on `develop` has not shown it (14 of the last 15 runs green, the other one the Playwright download).

## Expected fix

- Find why B's desk, rewritten by the migration (`cfg.local_to_desk` makes `stamp = saved.next(me, ...)` in `Agent::with_local_steps`), does not reach A when the link comes up late or the two stamps are compared before B's change is registered. Suspects: the desk handshake compares `(rev, sum)` before the bumped stamp is in the `SyncClock`; the migrated desk is sent once, on a link that is replaced right after (T-237 adopts the other agent's connection); the update is lost when both dial at the same time and one connection is dropped.
- Force the ordering with a deterministic test that fails before the fix. Fix the cause in the daemon; do not raise the 20 s limit.

## Notes

**Cause (a real lost update in the daemon, not the test).** Both test configs are pre-T-099 desks without `scenes`, so *both* agents migrate on start: each adds the default scenes, and B also moves its `[input] clipboard = false` into `[modules.b]`. Both are changes (`cfg.local_to_desk`), so each agent bumps the same saved stamp: A to `(rev 4, at tA, A)` and B to `(rev 4, at tB, B)`. They are siblings of the same base, and `DeskVersion::receive` keeps the one with the later `at` (ties go to A) whole. If B's start was later, B's desk won and A adopted the switch, which is what normally happens because the test starts A first. When A's stamp came out later (or in the same millisecond), A's desk, with no clipboard switch for B, won on both machines: B adopted it, its moved switch was gone for good, and A never saw `modules.b.clipboard == false`. Logged on a failing run under load: `A start rev 4 at …270 by A`, `B start rev 4 at …971 by B`, and B received A's version and adopted it. The same happens with two real machines upgraded from a pre-T-099 version: whichever starts later erases the other's migrated switches.

**Fix.** `Agent` keeps what its start-up migration moved (`MovedHere`: this machine's module switches and the `rev` of the version that carries them). After adopting the other's desk, `keep_moved_here` checks: if the version that now holds has the same `rev` as the migration (a simultaneous sibling, made without seeing this one), the switches go back on top as a new local change (`rev + 1`, sent to the other, which adopts it). As soon as a newer version holds, the record is dropped, so a later deliberate change by the other machine is never undone. `adopt_side` swaps its side along with the desk. The 20 s limit is unchanged.

**Tests.** `agent::tests::a_moved_setting_survives_the_other_machines_simultaneous_migration` builds both agents from the pre-T-099 files and hands B A's migration stamped 1 ms later (same `rev`, wins). Before the fix B ended with `modules.b.clipboard == None`; now B commits `rev 5` with the switch back, sends it, A adopts it, and a later change by A turning it on holds on B.

**Load runs** (`taskset -c 0,1` with 8 `yes` processes): before the fix, `a_local_setting_moved…` alone failed 7 of 300 (12 in parallel) at `network.rs:1003`; after, 0 of 600 runs of that test, and the whole `network` binary passed 120 of 120 runs.
